Abstract
Secure code review is critical at the pre-commit stage, where vul nerabilities must be caught early under tight latency and limited context constraints. Existing SAST-based checks are noisy and often
miss immature, context-dependent vulnerabilities, while standalone
Large Language Models (LLMs) are constrained by context win dows and lack explicit tool use. Agentic AI, which combine LLMs
with autonomous decision-making, tool invocation, and code nav igation, offer a promising alternative, but their effectiveness for
pre-commit secure code review is not yet well understood.
In this work, we introduce AgenticSCR, an agentic AI for secure
code review for detecting immature vulnerabilities during the pre commit stage, augmented by security-focused semantic memories.
Using our own curated benchmark of immature vulnerabilities,
tailored to the pre-commit secure code review, we empirically eval uate how accurate is our AgenticSCR for localizing, detecting, and
explaining immature vulnerabilities. Our results show that Agentic SCR achieves at least 153% relatively higher percentage of correct
code review comments than the static LLM-based baseline, and
also substantially surpasses SAST tools. Moreover, AgenticSCR
generates more correct comments in four out of five vulnerability
types, consistently and significantly outperforming all other base lines. These findings highlight the importance of Agentic Secure
Code Review, paving the way towards an emerging research area
of immature vulnerability detection.

harder to detect using techniques designed for post-hoc analysis

manifested [33, 40, 46]. As a result, many immature vulnerabilities
remain undetected and eventually propagate into main repositories.

code review tasks, operating within the command-line environment

3.3.1 Detector Subagent (
G,𝑎𝑑
). The ultimate goal (
G
) of our de tector subagent (𝑎𝑑 ) is to localize, detect, and explain immature vul nerabilities introduced during coding. Conventional large language
models (LLMs) are predominantly trained on general-purpose cor pora and therefore lack systematic expertise in security-oriented
code analysis. To address this limitation, we design the detector
subagent as an experienced secure code reviewer that analyzes
repository changes with an explicit security focus, guided by a cu rated set of Static Application Security Testing (SAST) rules stored
as long-term knowledge.
SASTs provide a rich source of rule-based knowledge for de tecting a wide range of coding issues. Prior studies have shown
that SAST can meaningfully assist code review. For example, SAST
warnings often overlap with developer comments, helping reduce
review effort [43], and can prompt open-ended questions that lead to higher-quality code revisions [48]. However, SASTs exhibit well known limitations. Since rules are applied purely statically, without
broader contextual reasoning, SASTs can generate substantial false
positives [53]. Instead of relying on SASTs to execute these rules
directly, subagents may benefit from using the rules as structured
knowledge for reasoning. Providing SAST rule definitions should
allow subagents to contextualize potential issues, improving pre cision while preserving broader reasoning capability. Therefore,
our detector subagent operates through the following workflow:
(1) load SAST rules into the semantic memory; (2) find a set of
code changes to review via autonomous tool calling; (3) examine
changes based on the SAST rules; and (4) apply SAST rules to the
given code changes. Finally, the detector subagent will produce the
following three outputs:
·(i) line-level localization that pinpoints the relevant line
range(s) and files within the staged diff that are related to im mature vulnerabilities, reducing developers
’
cognitive over head and accelerating remediation.
·(ii) a secure code review comment that explains the poten tial issue, summarizes evidence gathered from code context
and tool outputs, helping developers to reason about the
security implications of the pre-commit code change.
·(iii) a vulnerability type that is standardized using CWE
identifiers and names when validation succeeds [32]. Correct
vulnerability type explanation will help developers justify
the severity and impact of the issues and identify potential fixes [12].

4.3 Experimental Design
To evaluate the performance of AgenticSCR and the baselines, we
start from the 144 pre-commit code changes prepared in a sandbox
environment. Each sandbox environment consists of a working
directory that is checked out to the pre-commit code change stage.
Given the same sandbox environment, we run AgenticSCR, static
LLM-based secure reviewer, and three SAST tools to ensure a fair
comparison. The AgenticSCR will automatically run tools to find a
set of working code changes (i.e., Step 2 in the Detector Subagent)
and perform secure code review. For SAST tools, we run three SAST
tools through a bash command. Typically, SAST tools are executed
at the repository level. Thus, we filter out the warnings that are not
relevant to the set of working code changes, and only consider the
ones that are relevant to it for further evaluation. Since SAST tools
and AgenticSCR generate a different output format, we standardize
the outputs of the SAST tools by considering (1) the warning line;
(2) the warning content as a comment, and (3) the CWE type.

(13%) and Base+SAST+Guideline (12.6%). The performance loss that
we observed may have to do with the increased complexity and
potential interference introduced by heterogeneous knowledge
sources. While SAST rules are typically precise, pattern-driven,
and closely aligned with syntactic vulnerability manifestations, se cure code review guidelines tend to be broader, more abstract, and
context-dependent. Adding both into the detector subagent’
s long term semantic memory may therefore introduce semantic noise
or conflicting signals, making it harder for the agent to prioritize
highly actionable cues during detection.
6
Threats to Validity
Internal Validity. The construction of line-level vulnerability
ground-truths may be subject to individual bias. To mitigate this,
annotations followed a clearly defined operational definition of
actual vulnerability lines (i.e., must be the line(s) that are added or
modified in the pre-commit code change, but are later modified or
deleted in the bug-fixing commit; and must be associated with the
given CVE description and CWE vulnerability type). With a com parison with the actual CWE description and CWE vulnerability
type, this will reduce the reliance on subjective judgment.
Construct Validity. The % of relevant comments heaviy relies on
an LLM-as-a-judge [27], formulating as a binary classification task
whether a given code review comment is relevant to the actual vulnerability. However, like any LLMs, LLM judges are probablistic
and non-deterministic, which may introduce any model- or prompt specific biases in how a review comment is assessed. To mitigate this
concern, we conduct a manual verification of the judge outcomes
based on a manually labeled dataset of 70 code review comments.
Using the GPT-4.1, the judge achieves an F1 of 0.86, a Precision of
0.88, and a Recall of 0.86. Thus, we consider our judge to be accurate
enough for evaluating the comment relevance.
External Validity. Although the experiment of our AgenticSCR
is limited to our SCRBench, which includes a diverse set of open source projects and 5 vulnerability categories, we acknowledge that
the results may not be generalized to other programming languages,
projects, domains, or industrial codebases. Thus, we avoid strong
any generalization claims.
7
Conclusion
In this paper, we present AgenticSCR, an agentic AI secure code
review framework, targeting immature vulnerabilities in newly
changed code within a CLI environment. AgenticSCR leverages
augmented information in an agentic architecture, where subagents
autonomously access repository-level context while consulting a
security-focused semantic memories to detect issues (via SAST
rules) and validate comments (via a CWE tree). Our results confirm
that AgenticSCR can generate the highest number of comments
(17.5%) that are correctly localized and relevant with a valid vul nerability type, while generating 2-5 times fewer comments when
compared to the static LLM, SAST tools. These findings lead us to
conclude that augmenting agentic AI with security-focused seman tic memories can strengthen its performance in detecting immature
vulnerabilities at the pre-commit stage, thereby supporting secu rity shift-left by enabling earlier vulnerability detection during the
software development lifecycle.

将注意⼒从最相关的问题上转移开，这对 LLM 推理来说也可能是由于
上下⽂窗⼝有限⽽成⽴的情况。为了解决这个问题，我们从 Braz 等
⼈ [7] 和 Goncalves 等⼈ [22] 中综合了核⼼原则。具体来说，我们将
指南编码在⼀个 JSON ⽂件中，其中包含⼀系列指南条⽬。每个条⽬

input_validation 类，⼀个优先级级别，⼀个简短的标题，以及⼀组
以清单形式表述的 essential_checks 检查项。为了使指南能够直接⽤
于代码推理，我们还附带了 vulnerability_patterns，它将⼀个简要
的模式描述（例如，
request.getParameter() → 数据库查询) 使⽤⼀个最⼩的代码⽰例和
相关⻛险（例如，SQL 注⼊），以及简洁的缓解步骤和相关指南。这
些指南的表⽰应帮助引导代理的注意⼒到关键的安全模式（如未经验
证的输⼊流⼊ SQL 查询或⽂件路径）和建议的修复措施，⽽不会引⼊
不必要的认知负担或提⽰膨胀。
该指南带来了 3%的绝对改进，但相对于 SAST 规则低 24.3%（13）。
当⽐较 Base+指南和 Base 时，我们观察到
从 7.3%提⾼到 10.5%，表明纳⼊安全代码审查指南可以提⾼检测⼦
代理。尽管⽤指南（Base+Guideline+CWE）替换了 AgenticSCR 的
SAST 规则，但它只能⽣成 12.4%的正确评论，这⽐我们的

可以提⾼检测⼦代理，但不如 SAST。

与异构知识源带来的复杂性和潜在⼲扰有关。虽然 SAST 规则通常是精

6 对有效性的威胁
内部有效性。⾏级漏洞真实标签的构建可能受到个⼈偏⻅的影响。为
减轻这⼀问题，注释遵循了明确定义的漏洞⾏操作定义（即必须是预
提交代码变更中添加或修改的⾏，但在后续的补丁提交中被修改或删
除；并且必须与给定的 CVE 描述和 CWE 漏洞类型相关联）。通过与实
际 CWE 描述和 CWE 漏洞类型的⽐较，这将减少对主观判断的依赖。
构建效度。相关评论的%，很⼤程度上依赖于作为裁判的⼤型语⾔模
型 [27]，将其制定为⼀个⼆元分类任务，判断给定的代码评审评论是
否与实际漏洞相关。然⽽，像任何⼤型语⾔模型⼀样，⼤型语⾔模型
裁判是概率性和⾮确定性的，这可能会在评审评论的评估⽅式中引⼊
任何模型或特定提⽰偏差。为了缓解这⼀担忧，我们基于⼀个包含 70
条代码评审评论的⼿动标记数据集，对裁判结果进⾏了⼈⼯验证。使
⽤ GPT-4.1，裁判达到了 F1 值 0.86，精确度 0.88，召回率 0.86。因
此，我们认为我们的裁判⾜够准确，可以⽤于评估评论的相关性。
外部有效性。尽管我们的 AgenticSCR 实验仅限于我们的
SCRBench，该基准包含多样化的开源项⽬以及 5 个漏洞类别，我们
承认结果可能⽆法推⼴到其他编程语⾔、项⽬、领域或⼯业代码库。
因此，我们避免做出强烈的泛化声明。
7 结论
本⽂介绍了 AgenticSCR，⼀个代理式 AI 安全代码审查框架，旨在针对
CLI 环境中新修改代码中的不成熟漏洞。AgenticSCR 利⽤增强信息在
代理架构中，其中⼦代理⾃主访问仓库级上下⽂，同时咨询以安全为重
点的语义记忆来检测问题（通过 SAST 规则）并验证评论（通过 CWE
树）。我们的结果表明，AgenticSCR 可以⽣成最多 17.5%的正确定位
且与有效漏洞类型相关的评论，⽽与静态 LLM、SAST ⼯具相⽐，⽣成
的评论数量减少了 2-5 倍。这些发现使我们得出结论，通过为具有安全
导向的语义记忆的⾃主 AI 增加功能可以增强其在提交前阶段检测不成
熟漏洞的性能，从⽽通过在软件开发⽣命周期中更早地检测漏洞来⽀持
安全左移。
