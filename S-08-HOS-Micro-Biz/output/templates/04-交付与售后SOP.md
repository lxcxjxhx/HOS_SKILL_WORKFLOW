# 交付与售后 SOP

> **模块**: templates
> **文档编号**: TPL-0004
> **版本**: 1.0.0 | **最后更新**: 2026-07-26
> **适用阶段**: 冷启动 / 稳定期 / 扩张期

---

本 SOP 覆盖从订单确认到售后关闭的全链路标准作业流程,适用于 HOS 微商技术服务团队所有交付型项目。按项目阶段分为交付前准备、执行中同步、交付验收、售后支持、异常处理、归档规范、质量复盘七大模块,每个模块均含可复用模板与话术,可直接落地执行。

---

## 一、交付前准备 SOP

### 1.1 订单确认复核清单

订单进入交付前,必须完成以下复核项,任一项未通过即暂停启动开发。

| 复核项 | 核对内容 | 负责人 | 状态判定标准 |
|--------|----------|--------|--------------|
| 定金到账 | 核对收款账户流水,确认定金金额与报价单一致 | 运营 | 银行/微信/支付宝到账记录可查 |
| 需求文档 | 客户签字或聊天确认的需求清单 | 对接人 | 需求文档版本号已锁定 |
| 技术栈确认 | 客户指定或团队推荐的技术方案书面确认 | 技术 | 技术方案文档已双方确认 |
| 交付标准 | 功能验收标准、交付物清单明确 | 对接人 | 验收标准文档已发送客户 |
| 排期共识 | 交付日期、里程碑节点双方达成一致 | 项目经理 | 排期表已客户确认 |
| 合同/协议 | 电子协议或书面合同已签署 | 运营 | 协议文件已归档 |

复核流程:

```
订单确认复核流程
┌─────────────────────────────────────────┐
│ 1. 运营发起复核(订单创建后 4 小时内)     │
│    ↓                                    │
│ 2. 逐项核对六项复核内容                  │
│    ↓                                    │
│ 3. 全部通过 → 进入开发环境准备           │
│    部分未通过 → 标记阻塞项,通知对接人    │
│    ↓                                    │
│ 4. 阻塞项解决后重新复核                  │
│    ↓                                    │
│ 5. 复核通过,填写《项目启动单》           │
└─────────────────────────────────────────┘
```

### 1.2 开发环境准备清单

开发环境必须在复核通过后 24 小时内准备完毕。

| 类别 | 准备项 | 完成标准 |
|------|--------|----------|
| 代码仓库 | GitHub Private Repo 创建 | 仓库已创建,协作者已邀请 |
| 分支策略 | main/develop/feature 分支规范 | 分支保护规则已配置 |
| 开发环境 | 本地/云端开发环境搭建 | 环境可运行基础框架 |
| 数据库 | 开发库与测试库初始化 | 表结构脚本已提交 |
| 第三方服务 | API Key、SDK 配置 | 所需第三方服务已申请到位 |
| 文档空间 | Notion/飞书项目文档建立 | 需求文档、排期表已上传 |
| 沟通渠道 | 客户对接群建立 | 群成员齐全,公告已发 |

## 二、执行中进度同步 SOP

### 2.1 进度同步节奏

按项目周期长度分级同步频率,确保信息透明但不打扰客户。

| 项目周期 | 周期长度 | 同步频率 | 同步形式 | 客户参与节点 |
|----------|----------|----------|----------|--------------|
| 短周期 | 7 天以内 | 每 2 天 1 次 | 文字+截图 | 交付验收 |
| 中周期 | 7-30 天 | 每 3 天 1 次 | 文字+截图+视频 | 里程碑确认+验收 |
| 长周期 | 30 天以上 | 每周 1 次 | 文字+视频演示 | 每个里程碑+验收 |

补充规则:
- 重大节点(原型确认、功能联调、交付前)必须提前 1 天通知客户
- 出现延期风险时,24 小时内主动同步,不得隐瞒
- 客户主动询问时,2 小时内响应,不得隔夜

```

┌─────────────────────────────────────────────────┐

│    ↓                                            │
```

## 三、交付验收 SOP

### 3.1 交付前自检 Checklist

交付前 48 小时内完成自检,所有项必须为"通过"状态方可发起交付。

| 自检维度 | 检查项 | 通过标准 | 状态 |
|----------|--------|----------|------|
| 代码质量 | 代码规范符合团队标准 | Lint 无 error | □ |
| 代码质量 | 无明显冗余与硬编码 | Code Review 已完成 | □ |
| 代码质量 | 核心逻辑含必要注释 | 关键函数注释率>80% | □ |
| 功能完整性 | 需求文档功能点全覆盖 | 需求清单逐项核对 | □ |
| 功能完整性 | 主流程可正常走通 | 冒烟测试通过 | □ |
| 功能完整性 | 异常场景有处理 | 边界测试通过 | □ |
| 文档完整性 | README 部署文档 | 可按文档独立部署 | □ |
| 文档完整性 | 接口文档(API项目) | Swagger/Postman 可用 | □ |
| 文档完整性 | 操作手册(如需) | 客户可按手册操作 | □ |
| 兼容性 | 主流浏览器/设备适配 | Chrome/Safari/Edge 测试 | □ |
| 性能 | 首屏加载<3秒 | Lighthouse 评分>70 | □ |
| 安全 | 无明显安全漏洞 | SQL注入/XSS/CSRF 检查 | □ |

## 四、售后支持 SOP

### 4.1 售后范围界定

售后范围必须在交付时书面界定,避免边界模糊导致纠纷。

| 类别 | 判定标准 | 处理方式 | 费用 |
|------|----------|----------|------|
| Bug 修复 | 交付时已存在功能缺陷 | 免费修复 | 免费 |
| 功能微调 | 工时<2h 的小调整(文案、样式微调) | 免费处理 | 免费 |
| 功能优化 | 工时 2-8h 的体验改进 | 协商处理 | 视情况免费/收费 |
| 新增功能 | 需求文档外的全新功能 | 报价另签 | 收费 |
| 需求变更 | 改变原有功能逻辑 | 报价另签 | 收费 |
| 第三方故障 | 第三方服务/API 导致的问题 | 协助排查 | 免费(协助)/收费(修复) |
| 服务器/部署 | 客户方运维导致的问题 | 协助指导 | 免费(指导)/收费(代运维) |
| 内容更新 | 客户自行更新内容需协助 | 指导操作 | 免费(指导)/收费(代操作) |

边界判定流程:

```
售后需求边界判定
┌──────────────────────────────────────┐
│ 客户提出售后需求                     │
│   ↓                                  │
│ 是否在售后期内?                     │
│   否 → 按新单报价(见4.6)           │
│   是 ↓                               │
│ 是否为 Bug?                         │
│   是 → 免费修复                      │
│   否 ↓                               │
│ 是否在原需求范围内?                 │
│   是 + 工时<2h → 免费微调           │
│   是 + 工时≥2h → 协商处理           │
│   否 → 按新功能报价                  │
│   ↓                                  │
│ 记录到《售后修改记录》               │
└──────────────────────────────────────┘
```

### 4.2 售后响应时效承诺

按服务类型与紧急程度分级响应。

| 服务类型 | 响应时效 | 处理时效 | 说明 |
|----------|----------|----------|------|
| 紧急 Bug(功能不可用) | 2 小时内 | 24 小时内 | 影响核心流程的缺陷 |
| 一般 Bug(功能异常) | 4 小时内 | 48 小时内 | 功能可用但有错误 |
| 体验问题 | 8 小时内 | 3 个工作日内 | 不影响使用但体验不佳 |
| 功能咨询 | 12 小时内 | 即时解答 | 使用方法指导 |
| 新需求评估 | 24 小时内 | 评估后报价 | 售后期外或收费项 |

响应时效定义为"客户提出后到我方首次回复的时间",处理时效定义为"首次回复到问题解决的时间"。

## 五、异常处理 SOP

### 5.1 客户不满意应对流程

按不满意程度分级处理,确保问题不升级。

| 等级 | 表现特征 | 响应时效 | 处理层级 | 处理原则 |
|------|----------|----------|----------|----------|
| 轻微 | 局部功能或体验有意见,情绪平稳 | 4小时内 | 对接人 | 快速修复,安抚情绪 |
| 中度 | 对整体不满意,要求返工或退款 | 2小时内 | 对接人+技术负责人 | 评估责任,协商方案 |
| 严重 | 投诉、威胁差评、要求全额退款 | 1小时内 | 团队负责人+法务 | 证据保全,正式协商 |

| 第三方起诉侵权 | 开发前排查侵权风险,商用字体/图片授权 | 1.下线涉嫌内容 2.核查侵权事实 3.协商或应诉 |
| 客户未付款使用交付物 | 合同约定付款前知识产权不转移 | 1.发出停止使用通知 2.要求付款 3.法律途径 |
| 客户转售/转授权交付物 | 合同明确约定使用范围 | 1.核实转售事实 2.发函警告 3.索赔 |

知识产权约定必须在合同中明确:

```
合同知识产权条款(建议):

1. 交付物在尾款结清前,知识产权归乙方(交付方)所有,
   甲方(客户)仅可用于内部测试。
2. 尾款结清后,源代码使用权归甲方,但乙方保留:
   - 通用代码库与框架的复用权
   - 技术方案的再开发权
3. 甲方不得将交付物转售、转授权给第三方。
4. 第三方资源(字体/图片/插件)的授权由甲方自行购买,
   乙方仅负责集成。
5. 因甲方需求导致的知识产权侵权,责任由甲方承担。
```

## 六、交付物归档规范

### 6.1 代码归档

| 归档方式 | 说明 | 保留期限 | 用途 |
|----------|------|----------|------|
| GitHub Private Repo | 主仓库,含完整 Git 历史 | 永久 | 版本管理、协作 |
| 压缩包备份 | 每个里程碑打包一份 | 永久 | 灾难恢复、证据保全 |
| 本地冷备份 | 交付时打包存入冷存储 | 3 年 | 兜底备份 |

归档操作规范:

```
代码归档操作
1. GitHub 仓库设置为 Private
2. 添加客户为协作者(尾款结清后)
3. 每个里程碑创建 Tag:v1.0.0-m1
4. 交付时创建 Release:附交付物说明
5. 压缩包命名:[项目编号]-[日期]-[版本].zip
6. 压缩包内容:
   - /src           源代码
   - /docs          文档
   - /sql           数据库脚本
   - /config        配置示例
   - README.md      说明文档
   - CHANGELOG.md   变更记录
7. 压缩包存入:[归档路径]/[年份]/[项目编号]/
```

### 6.2 文档归档命名规范

```
文档命名规范:
[项目编号]-[文档类型]-[版本号]-[日期].md

示例:
P20260726-001-需求文档-v1.0.0-20260726.md
P20260726-001-部署文档-v1.0.0-20260726.md
P20260726-001-接口文档-v1.2.0-20260810.md
P20260726-001-验收确认单-v1.0.0-20260901.pdf
P20260726-001-售后记录-v1.0.0-20260915.md

文档类型编码:
- 需求文档:REQ
- 设计文档:DES
- 部署文档:DEP
- 接口文档:API
- 操作手册:MAN
- 测试报告:TST
- 验收单:ACC
- 售后记录:AFT
- 变更日志:CHG
- 复盘报告:REV
```

### 6.3 交付物快照留存

快照用于防篡改证据保全,在以下节点必须留存:

| 节点 | 快照内容 | 留存方式 |
|------|----------|----------|
| 需求确认 | 需求文档终版 + 客户确认聊天记录 | 截图+PDF+时间戳 |
| 交付时 | 代码仓库快照 + 交付物清单 | 压缩包+哈希值 |
| 验收时 | 验收确认单 + 演示录屏 | PDF+视频+时间戳 |
| 售后结束 | 最终代码 + 售后记录 | 压缩包+哈希值 |

哈希值生成与记录:

```
快照哈希记录
项目编号:________________
快照日期:____-__-__

┌──────────────┬──────────┬──────────────────┐
│ 快照内容     │ 文件名   │ SHA-256          │
├──────────────┼──────────┼──────────────────┤
│ 需求文档终版 │          │                  │
│ 交付代码包   │          │                  │
│ 验收确认单   │          │                  │
│ 最终代码包   │          │                  │
└──────────────┴──────────┴──────────────────┘

生成命令(powershell):
Get-FileHash [文件路径] -Algorithm SHA256
```

### 6.4 归档保留期限建议

| 归档类别 | 建议保留期限 | 保留理由 |
|----------|--------------|----------|
| 代码仓库 | 永久 | 复用、维护、证据 |
| 交付物压缩包 | 永久 | 证据保全 |
| 需求文档 | 永久 | 纠纷依据 |
| 验收确认单 | 永久 | 法律证据 |
| 售后记录 | 售后期+2年 | 追溯售后范围 |
| 沟通记录 | 项目结束后2年 | 纠纷依据 |
| 财务记录 | 按法规(10年) | 税务合规 |
