## 文档说明

本话术库是 HOS 微商技术服务运营体系中客户沟通环节的标准参考。文档按客户生命周期八大阶段编排,覆盖从初次咨询到危机处理的全部高频场景,每个场景均提供适用情境、可直接复制的话术模板与注意事项。

使用规则:

1. 话术为参考模板,实际使用需结合客户身份、项目类型与平台特性做最小化调整,严禁生搬硬套。
2. 方括号 `[X]`、`[XXX]` 等占位符为必填项,发送前必须替换。
3. 涉及报价、定金、售后条款的沟通,必须以书面形式(微信文字/邮件/确认单)留痕,口头承诺无效。
4. 本话术库与《需求确认 Checklist》《报价话术模板》《交付与售后 SOP》配套使用,不得单独引用。
5. 红线类需求(代考、代写、恶意攻击等)一律按《红线清单与拒绝话术》处理,不适用本库的话术安抚逻辑。

## 一、初次咨询话术

初次咨询是建立信任与筛选客户的第一道关口。核心目标:快速识别客户身份与需求类型,引导其提供结构化信息,同时对模糊或高风险需求进行分流。

### 1.1 学生课设咨询

**适用情境**:在校学生咨询课程设计、大作业、实验报告类需求,通常预算有限但需求相对标准。

```
您好,感谢咨询 HOS 技术服务。课设类项目我们做过比较多,
为了给您准确的方案和报价,麻烦先提供以下信息:

1. 学校与课程名称(便于评估评分标准与风格要求)
2. 老师下发的任务书或要求截图(如有)
3. 指定技术栈(如必须用 Java/Python,或由我们推荐)
4. 功能点清单(尽量逐条列出,越细越好)
5. 截止时间(精确到日,是否硬性截止)
6. 交付物要求(代码 / 文档 / PPT / 答辩辅导)

收到信息后我会在 2 小时内给您详细报价和工期方案。
所有方案均可先免费咨询,确认合适再合作。
```

**注意事项**:

- 学生客户预算敏感,开场不主动报价,先摸清需求体量。
- 主动询问"是否需要答辩辅导",这是高附加值增项。
- 如客户提及"代写""代做",立即按红线话术处理,不进入报价环节。

### 1.2 创业者工具开发

**适用情境**:创业者或小型团队需要开发内部工具、自动化脚本、MVP 原型,关注落地速度与可维护性。

```
您好,感谢咨询。工具开发类项目我们通常会先做需求梳理,
再给方案。麻烦先说明以下几点:

1. 工具要解决的核心业务问题(一句话概括)
2. 使用场景与使用频率(一次性 / 日常 / 高并发)
3. 是否需要部署上线,还是本地运行即可
4. 是否需要对接现有系统或第三方 API
5. 后续是否需要我方持续维护,还是交付后自行接管
6. 期望交付时间与预算区间

这类项目我们建议先做 30 分钟免费需求沟通,
明确边界后再报价,避免后续范围蔓延。
您方便的话可以约个时间语音过一遍。
```

**注意事项**:

- 创业者关注投入产出比,话术需突出"解决业务问题"而非"技术实现"。
- 主动提议语音沟通,文字难以厘清业务逻辑。
- 警惕"先做一版看看效果"的话术,需明确这是付费的 MVP 而非免费试做。

### 1.3 企业安全服务咨询

**适用情境**:企业客户咨询渗透测试、安全加固、等保合规等服务,通常需要正式报告与对公流程。

```
您好,感谢咨询。企业安全服务我们按标准化流程交付,
前期需要明确以下信息以便评估:

1. 企业名称与所属行业(金融 / 教育 / 电商 / 其他)
2. 测试目标范围(域名 / IP / App / 内网,需提供授权书)
3. 测试类型(黑盒 / 白盒 / 灰盒)
4. 是否需要符合特定合规框架(等保 2.0 / ISO 27001 / 行业规范)
5. 报告用途(内部整改 / 提交监管 / 投标资质)
6. 期望交付时间与是否需要现场支持

安全服务涉及授权与合规,正式合作前需签署
《授权测试协议》与《保密协议》,望理解。
```

**注意事项**:

- 任何安全服务必须先确认授权,无授权一律拒单。
- 企业客户通常需要开票,提前确认开票类型与税率。
- 报告用途决定深度与格式,内部整改与监管提交标准不同。

### 1.4 老客转介绍

**适用情境**:老客户介绍的新客户主动咨询,已有信任基础,转化率高,需体现对老客户的尊重。

```
您好,听 [老客户姓名] 提到您可能需要技术方面的支持,
感谢TA的推荐。为了让沟通更高效,先简单了解下:

1. [老客户姓名] 大概跟您介绍过我们的服务范围吗?
2. 您这次需要做的是什么类型的项目?
3. 有没有指定的时间要求或预算区间?
4. 是否有现成的需求文档或参考样例?

因为是 [老客户姓名] 介绍过来的,首次合作会在
标准报价基础上给您 [95 折 / 减 50 元] 的老友优惠。
需求确认后我会尽快出方案给您。
```

**注意事项**:

- 转介绍客户首次合作可给予适度优惠,但不得低于成本线。
- 主动提及老客户姓名,强化信任传递。
- 如转介绍客户为高风险需求,仍按红线流程处理,不因人情破例。

### 1.5 闲鱼来询

**适用情境**:客户通过闲鱼商品页私聊咨询,通常为价格敏感型,需快速引导至微信深度沟通。

```
您好,感谢咨询。闲鱼这边消息回复可能不及时,
建议加微信 [微信号] 详细聊,沟通效率更高。

方便的话先简单说下:
1. 要做什么项目(课设 / 毕设 / 工具 / 其他)
2. 用什么技术,或者由我们推荐
3. 什么时候要

加微信后我会给您出详细报价方案,
确认合适再合作,不合作也没关系。
```

**注意事项**:

- 闲鱼沟通效率低,优先引导加微信,但避免明显违规引流话术。
- 不在闲鱼直接报实价,避免被比价或被平台判定违规。
- 闲鱼客户价格敏感度高,需做好筛选,低质需求及时放弃。

### 1.6 小红书私信

**适用情境**:客户通过小红书笔记私信咨询,通常被内容吸引而来,信任度中等,需延续内容调性。

```
您好,感谢私信。看到您对 [笔记主题] 感兴趣,
我们可以提供这方面的技术服务。

为了给您准确建议,先了解下:
1. 您的具体需求是什么(越具体越好)
2. 是个人学习用途还是工作项目
3. 期望什么时候完成

方便的话加微信 [微信号] 聊,小红书消息容易漏看。
微信那边我会给您出详细方案,先免费咨询,合适再合作。
```

**注意事项**:

- 小红书私信引导加微信需委婉,避免被判定为导流违规。
- 延续笔记中的专业调性,不夸大不诱导。
- 主动复述笔记主题,强化"被内容吸引而来"的信任锚点。

### 1.7 社群咨询

**适用情境**:客户通过技术社群/微信群咨询,通常为半熟人关系,需兼顾社群形象与商业转化。

```
您好,看到您在群里问 [问题概述]。这类需求我们可以做,
详细聊的话加我微信 [微信号],群里消息容易刷屏。

简单先了解下:
1. 这是课程作业还是工作项目
2. 有没有指定技术栈
3. 截止时间紧不紧

加微信后我给您出方案,社群里的朋友过来一律有优惠,
您放心。
```

**注意事项**:

- 社群咨询避免在群内直接报价,防止被比价或引发群内争议。
- 提及"社群朋友有优惠"强化社群归属感,促进转化。
- 保持社群形象,沟通专业克制,不刷屏不硬广。

### 1.8 模糊需求咨询

**适用情境**:客户描述笼统,只说"做个系统""帮我写个程序",无法判断具体需求。

```
您好,感谢咨询。您提到的方向我大概理解,
不过要给您准确方案,需要把需求再细化一下。

方便先回答几个问题吗:
1. 这个 [系统/程序] 主要给谁用?用户角色有哪些?
2. 最核心的功能是什么?列出 1-3 个即可
3. 有没有参考的产品或样例可以发我看下
4. 是自己用的工具,还是要交付提交的作业/项目
5. 预期什么时候要,预算大概什么区间

需求越清晰,报价越准。如果您暂时说不清楚,
我们也可以约 15 分钟免费语音,我帮您梳理。
```

**注意事项**:

- 模糊需求严禁直接报价,否则后续必生纠纷。
- 提供语音梳理选项,体现专业度,同时筛选意愿客户。
- 如客户拒绝细化需求且坚持要"先报个价",礼貌婉拒,不进入报价环节。

## 二、需求确认话术

需求确认是报价前最关键的环节。核心目标:把模糊需求转化为可执行、可验收、可追溯的书面确认单,杜绝口头约定与后续扯皮。

### 2.1 需求模糊澄清

**适用情境**:客户已提供初步需求,但关键点模糊,需逐项澄清后再进入报价。

```
您发来的需求我看了,整体方向明白,但有几个点需要确认:

1. [功能点 A]:您期望的是 [方案 1] 还是 [方案 2]?
2. [功能点 B]:这里的"自动处理"具体指什么规则?
3. [功能点 C]:是否需要用户权限区分?还是所有用户相同?
4. 界面风格:有没有参考样例?或倾向简洁 / 商务 / 科技风?
5. 数据来源:是用现成数据集,还是需要爬取 / 录入?

为了避免后续返工,建议我们先把这几项确认清楚再开工。
您方便的话,我可以语音 10 分钟过一遍,效率更高。
确认后我会出书面需求确认单,双方签字后再启动。
```

**注意事项**:

- 澄清问题必须具体,给出可选项,避免开放式提问让客户无从回答。
- 每个澄清点都要落到书面确认单,口头确认无效。
- 如客户回避澄清,需评估是否为高风险客户,谨慎接单。

### 2.2 技术栈确认

**适用情境**:客户对技术栈无明确要求,或指定技术栈与需求不匹配,需专业建议。

```
关于技术栈,我给两个建议供您参考:

方案一:[推荐技术栈 A]
- 优势:[与需求匹配点]
- 劣势:[潜在问题]
- 适合场景:[描述]

方案二:[备选技术栈 B]
- 优势:[与需求匹配点]
- 劣势:[潜在问题]
- 适合场景:[描述]

我的建议是 [方案 X],原因是 [具体理由]。
不过如果您老师/团队有指定要求,请告知,我们按指定走。
另外,是否允许使用 AI 辅助生成代码?
部分课程对此有限制,需提前确认避免后续争议。
```

**注意事项**:

- 提供方案时必须给出优劣对比,不替客户做决定,但给出明确建议。
- 主动询问"是否允许 AI 辅助",这是学术合规的关键点。
- 如客户指定技术栈明显不合理,需诚实告知风险,不盲目接单。

### 2.3 交付物确认

**适用情境**:客户对交付物范围理解不清,需逐项明确,防止后续"我以为包含 X"的纠纷。

```
关于交付物,我列了个清单,您看下哪些需要,哪些不需要:

□ 源代码(完整可编译运行,含注释)
□ 可执行程序 / 安装包
□ 项目文档(需求 / 设计 / 测试)
□ 用户手册 / README
□ 答辩 PPT
□ 答辩讲稿 / 演示脚本
□ 演示视频
□ 数据库脚本 / 初始数据
□ 部署脚本 / Docker 镜像

另外需要确认:
- 代码注释要求:无 / 关键注释 / 详细注释
- 文档格式:Markdown / Word / PDF
- PPT 是否需要指定模板(您学校/企业的)

不在清单内的交付物视为不包含,后续如需新增另算费用。
确认后我会写入需求确认单,作为交付验收依据。
```

**注意事项**:

- 交付物清单必须穷尽,任何"默认应该有"的项目都要明示。
- 注释与文档格式需明确,这是高频纠纷点。
- 强调"清单外另算费用",防止范围蔓延。

### 2.4 截止时间确认

**适用情境**:客户对截止时间表述模糊,或截止时间过紧需评估加急。

```
关于交付时间,需要跟您确认几个点:

1. 最终截止时间是哪天?精确到日还是到时?
2. 这个截止是硬性的吗?(答辩日 / 提交日 / 合同节点)
3. 中间是否需要里程碑交付?(初版 / 修改版 / 终版)
4. 时区是按北京时间为准吗?(跨境订单需注意)

我这边的工作排期是这样的:
- 正常排期:X 天可交付(报价按正常档)
- 加急排期(1-3 天):需调整其他订单,加收 50%
- 特急排期(<24h):需加班赶工,加收 100%

建议预留 24-48 小时缓冲期,用于最终联调与修改。
您确认截止时间后,我会评估是否需要加急并告知报价。
```

**注意事项**:

- 截止时间必须精确到日,严禁"下周""月底"等模糊表述。
- 硬性截止需明确原因,评估缓冲空间。
- 加急费用需提前告知,不事后追讨。

## 三、报价沟通话术

报价是价值变现的关键节点。核心目标:让客户感知报价的合理性与依据,而非单纯比价;为后续议价预留空间,同时守住利润底线。

### 3.1 报价呈现

**适用情境**:需求已确认,需向客户呈现结构化报价单。

```
基于您确认的需求,本次项目报价如下:

【报价明细】
- 功能模块 A:[X] 元(工时 Xh × [时薪] × [系数])
- 功能模块 B:[X] 元(工时 Xh × [时薪] × [系数])
- 文档与 PPT:[X] 元
- 答辩辅导(可选):[X] 元
- 合计:[X] 元

【商务条款】
- 定金:50% 即 [X] 元,到账后开工
- 尾款:交付验收后支付 [X] 元
- 免费修改:2 次,范围限 Bug 与小调整
- 售后有效期:交付后 7 天

【交付承诺】
- 交付周期:X 天
- 中间进度同步:[频率,如每 2 天一次]
- 交付物清单:[附确认单]

报价依据为工时拆解 + 难度系数 + 紧急系数,
明细可查,无虚高。请您确认报价无误,
我发送收款方式。如有调整需求可随时沟通。
```

**注意事项**:

- 报价必须拆分明细,不报"一口价",便于客户感知价值。
- 主动说明报价依据,建立专业感与可信度。
- 定金比例与尾款节点必须明示,不留模糊空间。

### 3.2 价值锚定

**适用情境**:客户对报价有疑虑,需强化价值感知,避免陷入纯价格谈判。

```
理解您对价格的关注。这个报价的依据是这样的:

【工时投入】
- 需求分析:Xh
- 编码实现:Xh
- 测试调试:Xh
- 文档撰写:Xh
- 沟通修改预留:Xh
合计:Xh,按 [时薪] 元/小时核算

【价值包含】
- 不只是代码,还包含 [文档/PPT/答辩辅导]
- 2 轮免费修改,确保验收通过
- 7 天售后支持,交付后不撒手
- 代码含详细注释,可自主维护

【市场参考】
同类项目市场均价在 [X-X] 元区间,
我们的报价处于 [中位/偏下],且售后更全。

如果您预算有限,我们可以调整功能范围,
但不建议通过降低质量来压价,得不偿失。
```

**注意事项**:

- 价值锚定核心是"工时透明 + 服务全包",让客户感觉物超所值。
- 引用市场均价需真实,不虚构不夸大。
- 主动提供"减功能降价"选项,但强调不建议降质量。

### 3.3 议价应对

**适用情境**:客户压价,需在守住底线的前提下灵活应对。

```
价格我们可以这样谈:

方案一:减功能降价
- 去掉 [非核心模块],报价降至 [X] 元
- 后续如需补回,单独报价

方案二:延期折扣
- 交付时间从 X 天放宽到 Y 天
- 按正常排期走,报价降至 [X] 元(去加急)

方案三:全额预付优惠
- 一次性付清(而非定金+尾款)
- 给予 [5%] 折扣,报价 [X] 元

需要说明的是:
- 时薪基准已按市场下限核算,无法再降
- 质量与售后标准不会因价格调整而降低
- 单次让步不超过 10%,请您理解

您倾向哪个方案?或者有其他想法可以说。
```

**注意事项**:

- 议价优先"减价值"而非"减价格",守住单价底线。
- 提供多个方案让客户选择,而非被动接受压价。
- 明示让步边界,不无限退让。

### 3.4 加价说明

**适用情境**:执行中发现需求超预期或客户追加需求,需说明加价理由。

```
项目进行中我发现一个情况需要跟您确认:

【原需求】
[复述原始确认的需求点]

【实际情况】
[说明发现的复杂点或新增需求]
- 具体表现:[技术细节]
- 影响范围:[工时/技术/交付]
- 原因:[需求模糊/技术难点/第三方变化]

【加价方案】
- 新增工时:Xh
- 加价金额:[X] 元
- 工期影响:增加 X 天 / 无影响

【选项】
□ 同意加价,按新方案执行
□ 不加价,但需 [裁剪需求/延长工期/降低标准]
□ 暂停,双方再讨论

这个情况在开始前确实难以预判,现在跟您确认一下,
不擅自做主也不擅自加价。您怎么看?
```

**注意事项**:

- 加价必须基于事实,说明具体原因与影响,不模糊带过。
- 提供选项让客户决策,不强制加价。
- 加价需书面确认并更新需求确认单,口头同意无效。

## 四、执行跟进话术

执行阶段的核心目标:保持进度透明,主动同步,遇到问题及时沟通,避免客户因信息不对称产生焦虑或不信任。

### 4.1 进度同步

**适用情境**:项目执行中,按约定频率向客户同步进度。

```
【进度同步 - 第 X 次】
订单号:[XXX]  日期:[YYYY-MM-DD]

【已完成】
- [模块 A]:已完成,通过单元测试
- [模块 B]:已完成,待联调

【进行中】
- [模块 C]:预计 [日期] 完成

【待开始】
- [模块 D]:依赖 [模块 C],预计 [日期] 启动

【整体进度】
- 计划进度:X%
- 实际进度:X%
- 是否如期:是 / 延期 X 天(原因:[说明])

【需要您确认/配合的事项】
- [如有,列出;如无,写"暂无"]

按计划 [日期] 交付初版,届时同步给您。
```

**注意事项**:

- 进度同步必须定期,频率在开工时约定,不随意中断。
- 如实反映延期情况,不隐瞒不粉饰。
- 需客户配合的事项必须明示,避免被动等待。

### 4.2 遇到技术难点

**适用情境**:执行中遇到技术难点,可能影响工期或方案,需及时告知客户。

```
项目执行中遇到一个技术情况,需要跟您同步:

【情况说明】
- 难点:[具体技术问题]
- 影响:[工期/方案/性能]
- 发现时间:[日期]

【应对方案】
方案一:[替代技术方案]
- 优势:[说明]
- 代价:[工期/性能/功能差异]

方案二:[原方案攻关]
- 预计额外工时:Xh
- 成功率:[评估]

我的建议是 [方案 X],原因是 [说明]。
这个情况不影响 [核心功能],请您放心。
是否同意按 [方案 X] 执行?或需讨论其他方案?
```

**注意事项**:

- 技术难点必须第一时间告知,不拖延到交付才说。
- 提供解决方案而非单纯报问题,体现专业度。
- 涉及方案变更需书面确认,更新需求确认单。

### 4.3 需求变更确认

**适用情境**:客户在执行中提出新增或修改需求,需评估影响并确认。

```
您提的 [变更内容] 我收到了,评估如下:

【原需求】
[复述确认单中的原始需求]

【变更内容】
[描述客户提出的新需求]

【影响评估】
- 工时影响:增加 Xh / 无影响
- 费用影响:增加 [X] 元 / 无影响
- 工期影响:增加 X 天 / 无影响
- 技术影响:[说明]

【变更分类】
□ 免费修改范围(Bug/小调整,不另收费)
□ 重大变更(需重新报价,见下方)

【变更后报价】(如适用)
- 新增金额:[X] 元
- 变更后总价:[X] 元
- 变更后交付时间:[YYYY-MM-DD]

请您确认:
□ 同意变更,按上述条款执行
□ 不同意变更,按原需求执行
□ 需进一步讨论

确认后我会更新需求确认单,双方签字生效。
```

**注意事项**:

- 需求变更必须当场评估并书面确认,不口头答应。
- 严格区分"免费修改"与"重大变更",界限清晰。
- 变更确认单需双方签字,作为结算与验收依据。

## 五、交付验收话术

交付验收是订单闭环的关键节点。核心目标:引导客户按标准验收,明确验收期限,及时催收尾款,避免无限期拖延。

### 5.1 交付通知

**适用情境**:项目已完成,需向客户正式交付并引导验收。

```
项目已按需求确认单完成开发,交付物如下:

【交付物清单】
1. 源代码(已压缩):[下载链接]
2. 项目文档:[下载链接]
3. 答辩 PPT:[下载链接]
4. 数据库脚本:[下载链接]
5. 部署说明:[下载链接]

【验收标准】
按需求确认单中的功能清单逐项验收:
- F1 [功能描述]:□ 通过 □ 不通过
- F2 [功能描述]:□ 通过 □ 不通过
- F3 [功能描述]:□ 通过 □ 不通过

【验收期限】
请您在 [X] 天内(即 [日期] 前)完成验收并提出反馈。
逾期未提出异议视为验收通过,需支付尾款 [X] 元。

【远程演示】
如需远程演示或答辩辅导,可单独预约,
费用按 [X] 元/次计,非交付物默认包含项。

请下载交付物验收后告知结果,有问题随时找我。
```

**注意事项**:

- 交付物清单必须完整,与需求确认单一一对应。
- 验收期限必须明示,默认 3 天,逾期视为通过。
- 远程演示与答辩辅导为收费项,需提前说明。

### 5.2 验收引导

**适用情境**:客户收到交付物后不知如何验收,需引导其按流程操作。

```
收到交付物后,建议按以下步骤验收:

【第一步:环境准备】
- 按 README 安装依赖:[说明]
- 配置数据库:[说明]
- 如遇环境问题,48 小时内可协助解决(免费)

【第二步:功能验证】
- 按 [测试用例文档] 逐项测试
- 重点验证:F1 / F2 / F3(核心功能)

【第三步:反馈问题】
- 如发现问题,请截图 + 描述发送给我
- 我会在 [24/48] 小时内修复(免费修改范围内)
- 非 Bug 类调整需评估是否另收费

【第四步:确认验收】
- 全部通过后,请回复"验收通过"
- 我发送尾款收款方式
- 尾款到账后订单关闭,进入售后期

建议您在验收期内集中反馈,避免零散修改影响进度。
```

**注意事项**:

- 主动提供验收步骤,降低客户操作门槛。
- 明确"非 Bug 调整另收费",防止无限修改。
- 验收通过需客户明确回复,不默认通过。

### 5.3 尾款催收

**适用情境**:客户验收通过或逾期未反馈,需催收尾款。

```
您好,关于订单 [XXX] 的尾款事宜:

【订单状态】
- 交付日期:[YYYY-MM-DD]
- 验收期限:[YYYY-MM-DD](已到期 / 今日到期)
- 尾款金额:[X] 元

【验收情况】
- 您已确认验收通过 / 您未提出异议,按约定视为验收通过

【收款方式】
- 支付宝:[账号]
- 微信:[账号]
- 银行卡:[账号]

请您在 [X] 天内安排尾款支付,支付后请发送截图回执。
订单尾款结清后进入售后期(7 天免费修改)。

如对交付物有疑问,请在收到本消息后 [X] 天内提出,
逾期将视为验收通过且无异议。感谢配合。
```

**注意事项**:

- 尾款催收需礼貌但坚定,引用合同条款作为依据。
- 逾期未反馈需明确告知"视为验收通过",不留扯皮空间。
- 催收话术需留痕,作为后续纠纷处理证据。

## 六、售后处理话术

售后处理直接影响口碑与复购。核心目标:明确售后边界,快速响应合理诉求,对超范围诉求合理报价,到期前主动提醒。

### 6.1 免费修改

**适用情境**:客户在售后期内提出 Bug 修复或小调整,属免费范围。

```
收到您的反馈,问题描述我看了:

【问题】
[复述客户反馈的问题]

【评估】
- 分类:Bug 修复 / 小调整(免费范围)
- 响应时间:我会在 [24/48] 小时内处理
- 预计完成:[日期] 前给您

这个属于交付物的 Bug,免费修复,不另收费。
请稍等,我处理好发您。
```

**注意事项**:

- 免费修改必须快速响应,体现服务态度。
- 明确告知"免费",避免客户误以为要收费而不敢提。
- 修改完成后需客户确认,形成闭环。

### 6.2 超范围修改报价

**适用情境**:客户提出的修改超出免费范围(新增功能/重大调整),需报价。

```
您提的修改需求我评估了下:

【原需求】
[复述确认单原始需求]

【新需求】
[描述客户提出的新需求]

【评估】
- 分类:新增功能 / 重大调整(超出免费修改范围)
- 原因:[说明为什么超出范围]

【报价】
- 新增工时:Xh
- 报价金额:[X] 元
- 工期:X 天

【选项】
□ 接受报价,我立即处理
□ 暂不处理,后续再说
□ 调整需求范围,重新评估

这个修改属于需求扩展,需另收费,请您理解。
确认后我更新需求确认单并开始执行。
```

**注意事项**:

- 超范围判断需有理有据,引用确认单原始需求。
- 报价需明细,不模糊带过。
- 提供选项,不强推,尊重客户决策。

### 6.3 售后到期提醒

**适用情境**:售后期即将到期,需主动提醒客户,避免后续争议。

```
您好,关于订单 [XXX] 的售后事宜提醒:

【售后信息】
- 交付日期:[YYYY-MM-DD]
- 售后期:[YYYY-MM-DD] 至 [YYYY-MM-DD]
- 剩余天数:[X] 天

【售后范围】
- Bug 修复(免费)
- 小调整(免费)
- 新增功能(另收费)

【到期后说明】
售后期结束后,所有修改与维护将按 [X] 元/小时计费,
不再享受免费修改服务。

【建议】
如果您还有未反馈的问题,请在售后期内集中提出,
我优先处理。如无问题,感谢您的合作,期待下次合作。
```

**注意事项**:

- 售后到期提醒需提前 2-3 天,给客户反馈窗口。
- 明示到期后的计费标准,避免后续误解。
- 语气友好但清晰,不制造压迫感。

## 七、关系维护话术

关系维护是复购与转介绍的基础。核心目标:交付后持续关怀,自然引导转介绍与复购,不生硬推销。

### 7.1 交付后回访

**适用情境**:订单交付并验收后 1-2 周,主动回访客户使用情况。

```
您好,订单 [XXX] 交付已经 [X] 天了,回访下使用情况:

1. 项目使用是否顺利?有没有遇到问题?
2. 老师/团队反馈如何?
3. 还有什么需要我协助的吗?

如果一切顺利,麻烦您在 [闲鱼/朋友圈/社群] 帮我
留个评价或推荐一下,这对我们这种独立技术服务者
非常重要,先谢谢您。

后续有任何技术问题随时找我,老客户有优惠。
```

**注意事项**:

- 回访时机为交付后 1-2 周,过早打扰,过晚失去关怀感。
- 主动询问反馈,体现负责态度。
- 转介绍请求需自然,不强推,提供便利即可。

### 7.2 转介绍请求

**适用情境**:客户对服务满意,主动请求转介绍。

```
很高兴您对这次合作满意。有个不情之请:

如果您身边有同学/朋友也需要技术服务,
欢迎推荐过来。转介绍的客户我们一律给优惠:
- 新客户首单 [95 折 / 减 50 元]
- 您本人下次合作 [95 折 / 减 50 元]

这是我的联系方式 [微信号 / 闲鱼号],
方便的话可以转发给有需要的朋友。

当然,完全看您方便,不勉强。感谢这次合作。
```

**注意事项**:

- 转介绍请求需在客户表达满意后提出,不突兀。
- 提供双向优惠(新客+老客),激励更有效。
- 语气真诚,不施压,尊重客户选择。

### 7.3 老客复购邀约

**适用情境**:老客户有过往合作基础,主动邀约新合作或推荐新服务。

```
您好,好久不见。上次合作的 [项目名] 还顺利吧?

最近我们在做几个新方向的优惠活动,想着您可能感兴趣:
- [新服务 A]:[简述],[老客价 X] 元(原价 [Y] 元)
- [新服务 B]:[简述],[老客价 X] 元(原价 [Y] 元)

如果有需要可以随时找我,老客户优先排期。
如果暂时没需要也没关系,就当了解下行情。

另外,课设/毕设季快到了,如果学弟学妹有需要,
也欢迎推荐过来,转介绍有双向优惠。
```

**注意事项**:

- 老客邀约需有具体优惠,不打无准备之仗。
- 语气轻松,不强推,留余地。
- 结合时令(课设季/毕设季)更自然。

### 7.4 节日问候

**适用情境**:重大节日(春节/中秋/开学季)向老客户发送问候。

```
[节日名] 快乐!感谢您过去一年的支持。

过去一年我们合作了 [X] 个项目,很高兴能帮到您。
新的一年如果您有技术方面的需要,随时找我。
老客户一如既往有优惠。

祝您 [节日祝福语]。

[你的名字]  敬上
```

**注意事项**:

- 节日问候需简短真诚,不带推销话术。
- 提及过往合作数量,强化关系记忆。
- 群发需谨慎,尽量个性化,避免一眼群发感。

## 八、危机处理话术

危机处理是检验服务成熟度的试金石。核心目标:化解冲突,止损保口碑,对无理诉求守住底线,对合理诉求快速补救。

### 8.1 客户不满意

**适用情境**:客户对交付物表达不满,需安抚情绪并解决问题。

```
理解您的不满,我先表示歉意。我们一项一项来解决:

【您的反馈】
1. [复述客户不满点 1]
2. [复述客户不满点 2]

【我的回应】
1. 关于 [点 1]:[说明原因 / 承认问题 / 给方案]
2. 关于 [点 2]:[说明原因 / 承认问题 / 给方案]

【补救方案】
- 免费修改:[具体内容],[X] 天内完成
- 额外补偿:[如延长售后/赠送服务]

【后续承诺】
- 修改后请您再次验收
- 如仍不满意,我们继续协商

请您先消消气,把具体问题截图发我,我立即处理。
我们的目标是让您满意,不会撒手不管。
```

**注意事项**:

- 先安抚情绪,再解决问题,不与客户争辩对错。
- 如确实是我方问题,诚恳承认并补救,不推诿。
- 如属客户误解,耐心解释,引用确认单为据。

### 8.2 客户跑单

**适用情境**:客户交付后拒付尾款或失联,需按流程处理。

```
您好,关于订单 [XXX] 的尾款事宜,多次沟通未果,
现正式通知:

【订单信息】
- 交付日期:[YYYY-MM-DD]
- 验收期限:[YYYY-MM-DD](已逾期 X 天)
- 尾款金额:[X] 元

【合同依据】
- 需求确认单第 [X] 条:逾期未提出异议视为验收通过
- 需求确认单第 [X] 条:验收通过后支付尾款

【处理方案】
方案一:您在 [X] 天内支付尾款,订单正常关闭
方案二:如您对交付物有异议,请在 [X] 天内书面提出,
        我方核实后协商
方案三:逾期仍不支付且无书面异议,我方将:
        - 保留追究尾款的权利
        - 在 [平台/社群] 公示订单记录(脱敏)
        - 必要时采取法律手段

希望我们友好解决,请您在 [X] 天内回复。
```

**注意事项**:

- 跑单处理需有理有据,引用合同条款。
- 给出缓冲期与沟通选项,不一步到位撕破脸。
- 涉及公示或法律手段需谨慎,确保合规。

### 8.3 纠纷调解

**适用情境**:双方对需求范围或交付质量存在分歧,需第三方或平台介入调解。

```
关于订单 [XXX] 的争议,我方陈述如下:

【争议焦点】
[描述双方分歧点]

【我方依据】
1. 需求确认单第 [X] 条:[引用原文]
2. 沟通记录 [日期]:[截图说明]
3. 交付物清单:[与确认单对应]

【我方立场】
- 已按确认单完成交付
- 已提供 [X] 次免费修改
- 客户提出的 [新需求] 超出确认单范围

【调解诉求】
- 请调解方核实需求确认单与交付物
- 如确认我方已履约,请客户按约支付尾款
- 如确有交付瑕疵,我方愿在合理范围内补救

附:需求确认单、沟通记录截图、交付物清单
```

**注意事项**:

- 纠纷调解需以书面证据为主,情绪化表述无效。
- 完整附上需求确认单、沟通记录、交付物清单。
- 立场清晰但不咄咄逼人,留调解空间。

### 8.4 差评应对

**适用情境**:客户在平台留下差评,需公开回应并挽回口碑。

```
感谢您的反馈,对于让您不满的部分我们表示歉意。

【情况说明】
订单 [XXX] 于 [日期] 交付,我方已按需求确认单
完成 [功能清单]。交付后收到 [X] 次修改反馈,
均已处理。

【分歧点】
您提到的 [差评内容] 与确认单 [条款] 存在理解差异,
我方曾于 [日期] 沟通解释,未达成一致。

【补救意愿】
我们始终愿意在合理范围内补救:
- 售后期内的 Bug 修复(免费)
- 超出范围的修改(按 [X] 元/小时计费)

【致歉】
无论分歧如何,让您感到不满是我们的不足。
后续如有沟通意愿,欢迎随时联系:[联系方式]

[你的名字] / HOS 技术服务
```

**注意事项**:

- 差评回应需公开专业,不删评不互撕。
- 陈述事实,不情绪化,留第三方判断空间。
- 主动表达补救意愿,体现负责态度。

## 九、沟通渠道适配建议

不同平台的沟通特性与用户预期不同,话术需做适配,不可一套话术打天下。

### 9.1 微信(核心成交场)

```
【特性】
- 私密性强,适合深度沟通与商务确认
- 支持语音/视频/文件,沟通效率高
- 留痕方便,截图即可作为证据

【话术调整】
- 可发送长文本与结构化报价单
- 关键条款建议文字发送并要求客户回复确认
- 语音沟通后必须文字复述要点
- 朋友圈可作为案例展示,辅助成交

【禁忌】
- 不在朋友圈公开客户信息(脱敏处理)
- 不群发骚扰性促销话术
```

### 9.2 闲鱼(公域获客入口)

```
【特性】
- 平台规则限制多,导流话术易违规
- 客户价格敏感,比价严重
- 沟通效率低,消息易漏

【话术调整】
- 简短引导加微信,不在闲鱼深度沟通
- 不直接报实价,用"详聊"替代
- 商品描述突出卖点,私信只做需求初筛
- 避免明显引流话术,用"详聊""沟通"替代"加微信"

【禁忌】
- 不在闲鱼发微信号原文(用谐音/图片)
- 不承诺"100%通过""包过"等违规表述
```

### 9.3 小红书(种草获客)

```
【特性】
- 内容驱动,用户被笔记吸引而来
- 私信引导受限,需委婉
- 用户更关注"人设"与"故事",非纯商业

【话术调整】
- 延续笔记调性,专业 + 真诚
- 引导加微信需委婉:"消息容易漏看""详细聊更方便"
- 不主动报实价,先了解需求
- 主动复述笔记主题,强化信任锚点

【禁忌】
- 不发硬广链接
- 不在评论区公开报价
```

### 9.4 社群(信任培育场)

```
【特性】
- 半熟人关系,口碑传播强
- 群内沟通易被比价或引发争议
- 适合案例展示与技术分享,非硬广

【话术调整】
- 群内只做初步回应,深度沟通转私聊
- 不在群内报实价,用"私聊详谈"替代
- 主动提及"社群朋友有优惠",强化归属
- 保持社群形象,专业克制

【禁忌】
- 不群内刷屏硬广
- 不参与群内价格战
```

### 9.5 QQ群/贴吧(学生群体获客)

```
【特性】
- 学生群体为主,预算敏感
- 信息密度低,需重复触达
- 课设季流量集中

【话术调整】
- 话术直白,突出"学生价""课设季优惠"
- 强调"免费咨询""先聊不收费"降低门槛
- 主动提及学校/课程,建立同类感
- 提供往期案例(脱敏)增强信任

【禁忌】
- 不发与群主题无关的广告
- 不在考试期间推广代做类服务(红线)
```

### 9.6 邮件(企业客户正式沟通)

```
【特性】
- 正式商务场景,留痕完整
- 响应时效要求 24 小时内
- 适合发送报价单/合同/确认单

【话术调整】
- 使用正式商务邮件格式(称呼/正文/落款)
- 附件命名规范:[项目名]_[文档类型]_[日期].pdf
- 关键条款正文复述,不只依赖附件
- 邮件后跟微信/电话确认收悉

【禁忌】
- 不用口语化表达
- 不一邮件多主题
```

## 十、话术使用原则

### 10.1 三项基本原则

```
1. 真实原则
   - 话术内容必须真实,不夸大不虚构
   - 案例与数据需可验证,不编造
   - 承诺需可兑现,不空话

2. 边界原则
   - 涉及报价/条款/承诺的话术必须书面留痕
   - 口头沟通后必须文字复述确认
   - 不越权承诺(如"包过""包退款")

3. 专业原则
   - 技术问题给专业建议,不敷衍
   - 不懂的问题诚实告知,不装懂
   - 保持克制商务风格,不卑不亢
```

### 10.2 话术调整红线

```
以下调整严禁出现:

- 为成交而突破利润底线(低于时薪基准下限)
- 为成交而承诺无限制修改(范围蔓延风险)
- 为成交而隐瞒交付风险(技术难点/工期紧张)
- 为成交而突破合规红线(代考/代写/攻击)
- 为成交而诋毁同行(破坏行业生态)
```
