# 需求确认 Checklist

> **模块**: templates
> **文档编号**: TPL-0001
> **版本**: 1.0.0 | **最后更新**: 2026-07-26
> **适用阶段**: 冷启动 / 稳定期 / 扩张期

---

## 文档说明

本 Checklist 用于 HOS 微商技术服务运营助手中所有订单的接单前需求确认环节。任何订单在报价、签约、开工之前,必须完成本清单的全部勾选项,并由对接人书面确认。

使用规则:
1. 接单人按章节逐项核对,未勾选项必须给出说明
2. "高风险需求识别清单"出现任意命中即触发合规复核流程
3. 需求确认单经客户书面确认后归档,作为后续变更与结算依据
4. 本 Checklist 与《红线清单与拒绝话术》《报价话术模板》配套使用

## 一、基本信息确认

### 1.1 项目类型与背景

- [ ] 项目类型已明确(课设 / 毕设 / 工具 / 作业 / 竞赛 / 企业项目 / 其他)
- [ ] 项目所处阶段已确认(选题 / 开题 / 中期 / 结题 / 验收)
- [ ] 客户身份与角色已核实(在校学生 / 在职人员 / 企业对接人 / 中介)
- [ ] 客户所在学校或企业已记录(用于评估交付风格与验收标准)
- [ ] 项目所属课程或业务线已记录
- [ ] 项目预算区间已初步沟通(口头区间即可,正式报价后确认)
- [ ] 客户来源渠道已标注(社群 / 朋友推荐 / 平台 / 主动咨询)
- [ ] 是否存在中介转包已确认(中介订单需单独报备)

### 1.2 需求来源与参考材料

- [ ] 客户已提供完整需求文档或任务书
- [ ] 客户已提供参考样例 / 模板 / 往届作品(如有)
- [ ] 客户已提供老师或甲方的原始要求截图
- [ ] 客户已说明评分标准或验收标准(如已知)
- [ ] 客户已说明是否有指定教材 / 框架 / 工具
- [ ] 需求文档版本号已记录(避免后续需求版本混乱)
- [ ] 需求文档缺失项已列入"待补清单"并约定补齐时间

### 1.3 沟通记录留痕

- [ ] 初次咨询时间已记录
- [ ] 主要沟通渠道已确定(微信 / QQ / 飞书 / 邮件)
- [ ] 关键需求点已书面复述并发送客户确认
- [ ] 客户口头承诺已转化为书面记录(截图或文字回执)
- [ ] 沟通记录已归档至订单文件夹

## 二、技术需求确认

### 2.1 技术栈与框架

- [ ] 指定编程语言已确认(Java / Python / C++ / Go / JS / 其他)
- [ ] 指定框架已确认(Spring / Django / React / Vue / 其他)
- [ ] 指定数据库已确认(MySQL / PostgreSQL / MongoDB / SQLite / 其他)
- [ ] 是否允许使用第三方库 / 开源组件已明确
- [ ] 是否允许使用 AI 辅助生成代码已明确(部分课程禁止)
- [ ] 技术栈与客户环境兼容性已评估(如客户本地需运行)
- [ ] 技术栈与团队现有能力匹配度已评估(不匹配需转介或拒单)

### 2.2 功能需求清单

- [ ] 功能点已逐条列出并编号(F1、F2、F3...)
- [ ] 每个功能点的输入 / 输出 / 处理逻辑已描述
- [ ] 功能点的优先级已标注(必须 / 应该 / 可选)
- [ ] 功能点之间的依赖关系已梳理
- [ ] 是否包含用户登录 / 权限模块已确认
- [ ] 是否包含支付 / 订单 / 资金类模块已确认(触发合规复核)
- [ ] 是否包含数据采集 / 爬虫 / 接口对接已确认(触发合规复核)
- [ ] 是否包含外部 API 调用已确认(需评估 API 合规性与稳定性)

### 2.3 非功能需求

- [ ] 性能要求已确认(并发量 / 响应时间 / 数据量级)
- [ ] 兼容性要求已确认(浏览器 / 操作系统 / 移动端)
- [ ] 安全要求已确认(是否需要加密 / 鉴权 / 日志审计)
- [ ] 可用性要求已确认(是否需要部署上线 / 7x24 运行)
- [ ] 可维护性要求已确认(是否需要交付源码 / 文档 / 注释规范)
- [ ] 是否需要压力测试 / 安全测试报告已确认

### 2.4 运行环境与部署

- [ ] 客户是否提供服务器 / 云资源已确认
- [ ] 部署目标环境已确认(本地 / 校内服务器 / 公网云)
- [ ] 是否需要协助部署已确认(部署是否另收费)
- [ ] 是否需要提供 Docker 镜像 / 部署脚本已确认
- [ ] 域名 / 备案 / 证书由谁负责已确认

## 三、交付要求确认

### 3.1 交付物清单

- [ ] 源代码(完整可编译运行)是否交付
- [ ] 可执行程序 / 安装包是否交付
- [ ] 项目文档(需求 / 设计 / 测试)是否交付
- [ ] 用户手册 / README 是否交付
- [ ] 答辩 PPT 是否交付
- [ ] 答辩讲稿 / 演示脚本是否交付
- [ ] 演示视频是否交付(部分客户需要)
- [ ] 数据库脚本 / 初始数据是否交付

### 3.2 交付格式与规范

- [ ] 代码编码规范已确认(UTF-8 / GBK)
- [ ] 代码注释要求已确认(无 / 关键注释 / 详细注释)
- [ ] 代码风格规范已确认(是否需遵循特定 lint 规则)
- [ ] 文档格式已确认(Markdown / Word / PDF)
- [ ] PPT 模板是否指定(客户学校 / 企业模板)
- [ ] 交付包组织结构已约定(目录规范)

### 3.3 交付时间与里程碑

- [ ] 最终截止时间已确认(精确到日 / 时)
- [ ] 是否存在硬性截止(答辩日 / 提交日)已确认
- [ ] 中间里程碑已设定(初版 / 修改版 / 终版)
- [ ] 时区已确认(跨境订单需注意)
- [ ] 节假日因素已考虑(避免假期无法联调)
- [ ] 缓冲期已预留(建议截止前 24-48 小时完成终版)

### 3.4 售后与修改

- [ ] 免费修改次数已约定(默认 2 次)
- [ ] 免费修改范围已界定(仅 Bug / 含小调整 / 不含新增功能)
- [ ] 修改响应时长已约定(24 小时 / 48 小时)
- [ ] 售后有效期已约定(默认交付后 7 天)
- [ ] 超出范围修改的计费方式已说明
- [ ] 是否需要讲解 / 答辩辅导已确认(另收费项)
- [ ] 答辩辅导时长与形式已约定(线上 1 对 1 / 录播)

## 四、商务条款确认

### 4.1 报价与定金

- [ ] 正式报价已发送并经客户确认
- [ ] 报价明细已提供(功能拆分 / 工时 / 单价)
- [ ] 定金比例已确认(默认 50%,复杂项目可 60%-70%)
- [ ] 定金到账后再开工的原则已书面告知
- [ ] 尾款支付节点已确认(交付前 / 验收后 / 分阶段)
- [ ] 是否含税已说明(个人接单 / 企业开票)
- [ ] 开票类型已确认(普票 / 专票 / 不开票)

### 4.2 付款方式

- [ ] 收款渠道已确认(支付宝 / 微信 / 银行卡 / 对公)
- [ ] 收款账户已核对(避免误转)
- [ ] 大额订单(>5000 元)是否分阶段付款已确认
- [ ] 跨境订单支付方式已确认(PayPal / 加密货币需合规评估)
- [ ] 付款截图 / 回执已要求客户发送留痕

### 4.3 交付方式

- [ ] 交付渠道已确认(GitHub 私库 / 压缩包 / 网盘 / 远程演示)
- [ ] 交付后是否需要远程演示已确认
- [ ] 交付物验收标准已书面约定(功能清单逐项验收)
- [ ] 验收期限已约定(默认交付后 3 天内提出异议)
- [ ] 逾期未提出异议视为验收通过的条款已告知

### 4.4 知识产权与保密

- [ ] 源码版权归属已确认(归客户 / 归我方 / 共享)
- [ ] 是否允许我方作为案例展示已确认(脱敏后)
- [ ] 客户提供的资料保密义务已承诺
- [ ] 是否需要签署 NDA 已确认
- [ ] 是否包含客户敏感数据已评估(身份证 / 手机号 / 商业数据)

## 五、合规确认

### 5.1 红线筛查

- [ ] 已对照《红线清单与拒绝话术》逐条筛查
- [ ] 项目不涉及考试代考(在线考试 / 期末 / 认证考试)
- [ ] 项目不涉及论文代写(仅辅导修改,不代写正文)
- [ ] 项目不涉及恶意攻击(渗透测试仅限授权范围)
- [ ] 项目不涉及作弊工具(刷课 / 抢课 / 刷题脚本)
- [ ] 项目不涉及违法违规(赌博 / 色情 / 诈骗 / 黑产)
- [ ] 项目不涉及绕过身份认证 / 票务系统 / 验证码破解

### 5.2 学术合规

- [ ] 已确认项目用途是否为学术提交
- [ ] 已确认客户所在学校的学术诚信政策
- [ ] 辅导类服务已明确"授人以渔"边界(不代写核心代码)
- [ ] 课设 / 毕设类订单已评估学术风险等级
- [ ] 高风险学术订单已报备主管复核

### 5.3 数据与隐私

- [ ] 项目是否涉及个人信息采集已确认
- [ ] 项目是否涉及真实用户数据已确认
- [ ] 涉及数据的项目已评估《个人信息保护法》合规性
- [ ] 爬虫类项目已评估目标站点 robots.txt 与反爬条款
- [ ] 涉及接口对接的项目已确认 API 使用授权

### 5.4 内容合规

- [ ] 项目内容不涉及政治敏感
- [ ] 项目内容不涉及宗教歧视
- [ ] 项目内容不涉及未成年保护红线
- [ ] 项目内容不涉及虚假宣传 / 欺诈
- [ ] UGC 类项目是否需要内容审核机制已评估

## 六、风险提示与应对

### 6.1 需求风险

- [ ] 需求是否模糊已评估(模糊度:低 / 中 / 高)
- [ ] 需求是否存在"看情况"等不确定表述
- [ ] 客户是否频繁变更需求(历史行为参考)
- [ ] 需求变更应对条款已写入确认单
- [ ] 高模糊度订单是否采用"分期确认 + 分期报价"已决策

### 6.2 交付风险

- [ ] 截止时间是否过紧已评估(工期 ≤ 3 天为高风险)
- [ ] 技术难点是否已识别并评估可行性
- [ ] 是否存在第三方依赖风险(API 不稳 / 库版本冲突)
- [ ] 是否存在环境部署风险(客户环境复杂)
- [ ] 是否需要加班赶工已评估(赶工订单加收 20%-50%)

### 6.3 商务风险

- [ ] 客户信用已评估(新客户 / 老客户 / 朋友推荐)
- [ ] 定金是否到账已确认(未到账不开工)
- [ ] 是否存在"先做着,做完再付"的话术(一律拒绝)
- [ ] 是否存在第三方代付(需核实代付人身份)
- [ ] 大额订单是否签署正式合同(>10000 元建议签合同)

### 6.4 沟通风险

- [ ] 客户沟通风格已评估(爽快 / 拖延 / 挑剔)
- [ ] 客户是否提供清晰反馈(历史记录参考)
- [ ] 是否存在时差 / 语言障碍
- [ ] 关键决策点是否要求客户书面确认(避免口头扯皮)
- [ ] 是否已指定项目对接人(避免多头沟通)

## 七、需求确认话术模板

### 7.1 初次咨询话术

```
您好,感谢咨询 HOS 技术服务。为了给您提供准确的方案和报价,
麻烦先提供以下信息:

1. 项目类型(课设 / 毕设 / 工具开发 / 其他)
2. 您的技术栈要求(指定语言 / 框架,或由我们推荐)
3. 功能需求清单(尽量详细,有任务书可直接发我)
4. 期望交付时间
5. 交付物要求(代码 / 文档 / PPT / 答辩辅导)

收到信息后我会在 [X] 小时内给您详细报价和工期方案。
```

### 7.2 需求模糊时澄清话术

```
您发来的需求我看了,整体方向明白,但有几个点需要确认一下:

1. [功能点 A]:您期望的是 [方案 1] 还是 [方案 2]?
2. [功能点 B]:这里的"自动处理"具体指什么规则?
3. [功能点 C]:是否需要用户权限区分?还是所有用户相同?
4. 界面风格:有没有参考样例?或者倾向简洁 / 商务 / 科技风?

为了避免后续返工,建议我们先把这几项确认清楚再开工。
您方便的话,我可以语音 10 分钟过一遍,效率更高。
```

## 八、需求变更确认流程

### 8.1 变更触发条件

```
以下情况触发需求变更流程,需重新确认并可能重新报价:

1. 新增功能模块(原确认单未包含)
2. 功能逻辑重大调整(非 Bug 修复)
3. 技术栈变更(如 Java 改 Python)
4. 交付物范围扩展(如新增 PPT、新增答辩辅导)
5. 截止时间提前(且工期压缩超过 30%)
6. 界面风格推翻重做(非细节调整)

以下情况不触发变更流程,视为免费修改范围:

1. Bug 修复(功能未按确认单实现)
2. 文字与排版小调整
3. 配色 / 字体微调
4. 注释补充
5. 文档错别字修正
```

### 8.2 变更确认模板

```
【需求变更确认单】

订单编号:[XXX]
原确认单编号:[XXX]
变更日期:[YYYY-MM-DD]

变更内容:
1. [原需求]:...
   [变更为]:...
2. [原需求]:...
   [变更为]:...

变更影响:
- 工期影响:增加 [X] 天 / 无影响
- 费用影响:增加 [X] 元 / 无影响
- 其他影响:...

变更后总价:[X] 元
变更后交付时间:[YYYY-MM-DD]

客户确认:
□ 同意变更,按上述条款执行
□ 不同意变更,按原需求执行

客户签字(电子):___________  日期:___________
```

### 8.3 重新报价触发条件

```
触发重新报价的阈值:

1. 变更涉及新增功能模块 → 必须重新报价
2. 变更涉及工时增加超过总工时 20% → 必须重新报价
3. 变更涉及技术栈调整 → 必须重新报价
4. 变更涉及第三方资源(如付费 API、服务器)→ 必须重新报价
5. 累计变更次数超过 3 次 → 建议重新评估整体报价

不触发重新报价的情况:

1. 工时增加不超过总工时 10% → 免费修改
2. 纯 Bug 修复 → 免费修改
3. 文档小调整 → 免费修改
```

## 十、高风险需求识别清单

### 10.1 红线信号(命中即拒单)

```
【代考类信号】
- 客户要求"替我参加在线考试"
- 客户要求"考试期间远程操作我的电脑"
- 客户要求"帮我做考试系统"实为绕过监考
- 客户要求开发"自动答题""考试外挂"
- 客户询问"能否代考某某认证"

【代写类信号】
- 客户要求"帮我写毕业论文正文"
- 客户要求"直接给我完整代码,我自己也看不懂"
- 客户拒绝任何辅导形式,只要成品
- 客户要求"不要注释,像我自己写的"
- 客户要求"查重率低于 X%"(代写特征)

【攻击类信号】
- 客户要求"帮我黑入某某系统"
- 客户要求"破解某某账号密码"
- 客户要求"DDoS 某某网站"
- 客户无法提供渗透测试授权书
- 客户要求开发"木马""后门""键盘记录器"

【作弊工具类信号】
- 客户要求开发"刷课脚本""自动播放"
- 客户要求开发"抢课脚本""秒杀外挂"
- 客户要求开发"自动刷题""题库爬取后自动答题"
- 客户要求开发"多开""改分""绕过验证"

【违法黑产类信号】
- 客户要求开发"赌博网站""博彩系统"
- 客户要求开发"色情直播""成人平台"
- 客户要求开发"资金盘""传销系统"
- 客户要求开发"诈骗话术系统""钓鱼页面"
- 客户要求"洗钱""跑分"相关功能
- 客户要求开发"群控""养号""薅羊毛"系统
```

### 10.2 灰色地带信号(需合规复核)

```
【需复核的灰色需求】
- 辅导 vs 代写边界模糊(客户说"帮我改改"实为代写)
- 授权测试 vs 恶意攻击边界模糊(客户说"是自己公司系统"但无授权)
- 数据采集 vs 爬虫滥用边界模糊(目标站点反爬严格)
- 自动化工具 vs 作弊工具边界模糊(如"自动填表"是否影响公平)
- 安全研究 vs 武器化边界模糊(如"漏洞复现"是否提供攻击代码)

处理方式:
1. 暂停报价,要求客户提供补充材料(授权书、学校政策、业务说明)
2. 将需求与补充材料提交合规复核
3. 合规复核通过后方可继续,不通过则拒单
4. 复核记录归档
```

### 10.3 风险客户行为信号

```
【客户行为风险信号】
- 急催开工但不愿付定金
- 拒绝书面确认,只愿意口头沟通
- 需求描述刻意模糊,追问时回避
- 要求"先做一部分看看效果再决定"
- 频繁压价并暗示"找别人也行"
- 拒绝提供真实身份或学校信息
- 沟通中提及"别问那么多,照做就行"
- 要求签订免责条款(典型黑产特征)

处理方式:
1. 提高定金比例至 60%-70%
2. 强制要求书面需求确认
3. 必要时拒绝接单
4. 保留沟通记录以备查证
```
