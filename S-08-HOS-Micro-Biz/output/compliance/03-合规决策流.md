# 合规决策流

> **模块**: compliance
> **文档编号**: CMP-0003
> **版本**: 1.0.0 | **最后更新**: 2026-07-26
> **适用阶段**: 冷启动 / 稳定期 / 扩张期

---

## 文档说明

本文档定义 HOS 微商技术服务运营的全链路合规决策流程,覆盖从客户咨询到交付售后的每一个合规判断节点。所有订单必须经过三层过滤模型评估,任何红线层命中项均直接终止合作。

**适用对象**: 接单主理人、执行人员、售后人员。
**执行原则**: 宁可拒单,不可踩线;书面留痕,口头无效;无法判定时,默认从严。

---

## 一、合规决策框架:三层过滤模型

### 1.1 模型总览

```
┌─────────────────────────────────────────────────────────┐
│              客户需求 / 咨询输入                          │
└─────────────────────┬───────────────────────────────────┘
                      ▼
┌─────────────────────────────────────────────────────────┐
│  第一层:红线层(不可逾越)                                │
│  - 法律法规红线                                          │
│  - 平台禁售红线                                          │
│  - 道德伦理红线                                          │
│  命中任意一条 → 直接拒绝,终止沟通                       │
└─────────────────────┬───────────────────────────────────┘
                      ▼ (红线未命中)
┌─────────────────────────────────────────────────────────┐
│  第二层:灰色层(需判定)                                 │
│  - 知识产权合规                                          │
│  - 数据使用合规                                          │
│  - 技术选型合规                                          │
│  - 授权与资质合规                                        │
│  需评估风险等级,制定缓释方案后方可推进                  │
└─────────────────────┬───────────────────────────────────┘
                      ▼ (灰色风险可接受)
┌─────────────────────────────────────────────────────────┐
│  第三层:执行层(规范化)                                 │
│  - 合同与定金                                            │
│  - 需求确认与变更管控                                    │
│  - 交付验收与售后                                        │
│  按标准流程执行,全程留痕                                │
└─────────────────────────────────────────────────────────┘
```

### 1.2 三层过滤判定要点

**第一层 红线层(一票否决)**

| 红线类别 | 判定要点 | 处置 |
|---|---|---|
| 法律法规 | 涉及违法犯罪(作弊 / 黑产 / 破解 / 侵权复刻) | 直接拒绝 |
| 平台禁售 | 平台明确禁止销售的服务或商品 | 直接拒绝 |
| 道德伦理 | 代写论文 / 代考试 / 损害他人合法权益 | 直接拒绝 |
| 未授权测试 | 渗透测试 / 漏洞利用无书面授权 | 直接拒绝 |

**第二层 灰色层(风险评估)**

| 灰色类别 | 判定要点 | 处置 |
|---|---|---|
| 知识产权 | 开源组件许可证 / 商业软件复刻 / 素材版权 | 核查许可证,不合规则拒绝或更换方案 |
| 数据使用 | 爬虫 / 个人信息 / 竞品数据 | 核查数据来源合法性,违规则拒绝 |
| 技术选型 | 技术方案是否存在滥用风险 | 评估可控性,不可控则调整方案 |
| 授权资质 | 客户是否有权委托该事项 | 要求提供授权证明,无授权则拒绝 |

**第三层 执行层(规范流程)**

| 执行要点 | 规范 |
|---|---|
| 合同与定金 | 书面确认 + 定金到账再启动 |
| 需求管控 | 需求确认单 + 变更重新报价 |
| 交付验收 | 验收标准明确 + 书面确认 |
| 售后服务 | 范围期限明确 + 全程留痕 |

### 2.2 接单决策要点

**Step 1 需求理解**

```
要点:
- 复述客户需求,确认理解无误
- 询问项目用途、使用场景、交付期限
- 识别模糊表述("帮忙看一下""随便弄一下"),要求明确化
- 判断客户是否为最终使用方,排查代发/转包
```

**Step 2 红线扫描**

```
要点:
- 对照 01-红线清单与拒绝话术 逐项核查
- 重点关注:考试作弊、代写论文、抢课刷课、渗透测试(无授权)、
  刷单黑产、破解盗版、侵权复刻
- 命中任一红线,直接进入拒绝流程,不再继续评估
```

**Step 3 灰色判定**

```
要点:
- 知识产权:开源组件许可证核查(GPL/MIT/Apache 等)
- 数据使用:数据来源合法性核查(爬虫目标 robots.txt、个人信息授权)
- 技术选型:方案是否可被滥用(如自动化工具的合规边界)
- 授权资质:客户是否有权委托(如系统所有者授权、数据所有者授权)
- 无法判定的,要求客户提供书面授权或资质证明
```

**Step 4 风险评估**

```
要点:
- 评估风险发生概率(高/中/低)
- 评估风险影响程度(高/中/低)
- 对照风险等级评估矩阵确定等级(参见 02-风险防控checklist 第七章)
- 极高/高风险:拒绝或要求客户书面接受全部风险
- 中风险:制定缓释方案(授权书、合同条款、分阶段交付等)后可接单
- 低/可接受风险:正常接单,按标准流程执行
```

**Step 5 接单执行**

```
要点:
- 签订书面合同或确认需求确认单(含服务范围、价格、工期、售后)
- 收取定金(按金额区间规则,参见 02-风险防控checklist 第五章)
- 定金到账后启动实质性工作
- 进入执行层流程
```

**需求变更合规检查点**:

```
[ ] 1. 变更内容是否触及红线(即使原需求合规,变更可能踩线)
[ ] 2. 变更是否涉及新的知识产权(新增开源组件/素材)
[ ] 3. 变更是否涉及新的数据使用(新增数据源/数据处理)
[ ] 4. 变更是否涉及新的授权需求(访问新系统/使用新账号)
[ ] 5. 变更是否超出我方技术能力(评估可行性)
[ ] 6. 变更是否导致工期/价格重大变化(重新报价)
[ ] 7. 变更是否需要客户补充授权文件
[ ] 8. 变更确认是否已书面化(聊天记录明确"确认")
```

### 4.2 知识产权确认

**知识产权归属约定**:

| 交付物类型 | 默认归属 | 约定方式 |
|---|---|---|
| 定制开发代码 | 客户(尾款结清后) | 合同明确约定 |
| 通用组件/工具 | 我方(授权客户使用) | 授权范围明确 |
| 设计稿/文案 | 客户(尾款结清后) | 合同明确约定 |
| 技术方案文档 | 我方 | 可授权客户查阅 |
| 第三方素材 | 原权利人 | 标注来源与许可证 |

**知识产权确认检查点**:

```
[ ] 1. 合同已明确约定交付物知识产权归属
[ ] 2. 通用组件/工具与我方自有代码已区分标注
[ ] 3. 第三方素材来源已记录(便于后续维权/举证)
[ ] 4. 开源组件清单已整理(LICENSE 文件保留)
[ ] 5. 客户未要求我方转让通用工具/框架所有权
[ ] 6. 客户未要求我方为其侵权行为承担连带责任
[ ] 7. 尾款未结清前,知识产权不发生转移
[ ] 8. 知识产权确认记录已归档
```

### 4.3 保密义务履行

**保密范围**:

```
我方对客户承担保密义务的内容:
- 客户的商业信息(商业模式、运营数据、客户名单)
- 客户的技术信息(技术方案、源码、配置)
- 客户提供的资料(文档、数据、账号)
- 合作事实本身(如客户要求保密)

客户对我方承担保密义务的内容:
- 我方的技术方案与实现细节
- 我方的报价与成本结构
- 我方的通用工具与框架
- 合作事实本身(如我方要求保密)
```

**保密义务履行检查点**:

```
[ ] 1. 涉密信息已标注保密级别(内部/机密/绝密)
[ ] 2. 涉密信息存储于受控环境(加密/访问控制)
[ ] 3. 涉密信息不在公开渠道(朋友圈/技术文章)泄露
[ ] 4. 客户案例展示已获客户授权或脱敏处理
[ ] 5. 项目结束后,客户敏感数据已按约定删除/归还
[ ] 6. 保密期限已明确(默认合作结束后 2 年)
[ ] 7. 违约责任已约定(合同条款)
[ ] 8. 保密协议(NDA)已签署(大额订单/敏感项目)
```

## 五、典型场景决策示例

### 案例1:客户要求"帮忙看一下考试系统漏洞"

**场景描述**:
客户通过微信咨询,称"我们学校的考试系统好像有 bug,你帮忙看一下漏洞在哪,顺便给我一个利用方法,我想验证一下"。

**合规判定**: 红线,直接拒绝。

**决策依据**:
- 未提供系统所有者书面授权,属于未授权测试
- "利用方法"涉及漏洞利用,涉嫌违法
- 即使客户声称是系统所有者,无书面授权亦不可执行

**应对话术**:
```
"您好,漏洞测试需要系统所有者的书面授权,我无法在未授权情况下
进行任何安全测试,这涉及法律风险。如果您是系统所有者,
请提供书面授权书(含测试范围、时间、责任人),我们可以
按合规流程提供安全评估服务。"
```

**替代方案**:
- 引导客户提供书面授权,转为合规渗透测试服务
- 推荐客户联系系统厂商或学校信息中心处理

### 案例2:客户要求"写一个抢课脚本"

**场景描述**:
客户称"学校选课系统太难抢了,你帮我写个自动抢课脚本,能自动登录、自动刷新、自动提交"。

**合规判定**: 红线,直接拒绝。

**决策依据**:
- 抢课脚本属于自动化作弊工具,违反学校规定
- 可能破坏选课公平性,损害其他学生权益
- 涉及未经授权的系统自动化操作

**应对话术**:
```
"抱歉,抢课脚本属于自动化作弊工具,违反学校选课规定,
也可能影响其他同学的公平选课,我无法提供此类服务。
建议您关注学校的补退选政策,或联系教务处反映选课系统问题。"
```

**替代方案**:
- 无合规替代方案,直接拒绝
- 可建议客户合理规划选课策略

### 案例3:客户要求"基于某开源项目做毕设"

**场景描述**:
客户称"我看到 GitHub 上有个开源项目很好,你帮我基于它改一下作为我的毕设,加点新功能就行"。

**合规判定**: 灰色,需判定。

**决策依据**:
- 需核查开源项目许可证类型
- GPL/AGPL 许可证:衍生作品必须开源,但作为毕设可接受
- MIT/BSD 许可证:保留版权声明即可
- 客户声称"作为毕设",涉及学术诚信问题,需明确"辅导"边界

**应对话术**:
```
"基于开源项目做二次开发是可以的,但需要先确认两点:
1. 开源项目的许可证类型,我会核查合规性并保留版权声明;
2. 作为毕设,我可以提供技术辅导与代码实现协助,
   但学术诚信要求您理解并参与核心工作,我不能代写整篇毕设。
请提供项目链接,我先评估许可证与工作量。"
```

**替代方案**:
- 提供技术辅导服务(讲解原理、协助调试)
- 协助实现特定功能模块(客户需参与设计)
- 拒绝代写整篇毕设(触及学术诚信红线)

### 案例4:客户要求"部署一个 ChatGPT 镜像售卖"

**场景描述**:
客户称"你帮我部署一个 ChatGPT 镜像站,我想对外售卖 API 接口,利润对半分"。

**合规判定**: 红线,直接拒绝。

**决策依据**:
- 未经 OpenAI 授权镜像其服务,构成侵权
- 售卖未经授权的 API 接口,涉嫌违法经营
- 可能违反 OpenAI 服务条款,导致法律风险

**应对话术**:
```
"抱歉,未经 OpenAI 授权镜像其服务并售卖 API,涉及侵权与违法经营,
我无法提供此类服务。如果您想做 AI 相关业务,我可以协助您:
1. 接入合规的 AI API(如国内厂商的开放平台);
2. 搭建基于开源模型的私有部署(如 LLaMA 系列);
3. 开发合规的 AI 应用产品。
欢迎咨询合规方案。"
```

**替代方案**:
- 接入合规 AI API(百度文心、阿里通义、智谱等)
- 基于开源模型(如 LLaMA、ChatGLM)私有部署
- 开发合规的 AI 应用产品

### 案例5:客户要求"分析竞品数据库"

**场景描述**:
客户称"我竞争对手的数据库好像没设密码,你帮我连上去看看他们的数据,分析一下他们的商业模式"。

**合规判定**: 红线,直接拒绝。

**决策依据**:
- 未经授权访问他人数据库,涉嫌非法侵入计算机系统罪
- 获取他人商业数据,涉嫌侵犯商业秘密
- 即使数据库"没设密码",不代表授权访问

**应对话术**:
```
"抱歉,未经授权访问他人数据库属于违法行为,无论是否设有密码,
我都不会提供此类服务,这涉及刑事风险。如果您需要竞品分析,
我可以协助您通过合规渠道收集公开信息(官网、公开报告、
专利数据库等),提供商业分析服务。"
```

**替代方案**:
- 合规竞品分析(基于公开信息)
- 商业情报收集(公开渠道)
- 拒绝任何未授权访问

### 案例6:客户要求"代写论文"

**场景描述**:
客户称"我论文写不出来,你帮我代写一篇,价格好商量。注意,我不是让你代写,我是让你'辅导'我写,你懂的"。

**合规判定**: 红线,直接拒绝。

**决策依据**:
- 代写论文违反学术诚信,可能违反校规与学位条例
- "辅导"为话术包装,实质仍为代写
- 不论如何表述,代写行为本身不可接受

**应对话术**:
```
"抱歉,代写论文违反学术诚信,我无法提供此类服务,
无论以何种名义。如果您需要学术写作辅导,我可以提供:
1. 论文结构与逻辑梳理建议;
2. 文献检索与阅读方法指导;
3. 写作技巧与语言润色建议。
但核心内容必须由您本人完成。"
```

**替代方案**:
- 学术写作辅导(方法论指导)
- 文献检索指导
- 论文润色(已完成的初稿)
- 拒绝代写任何形式的核心内容

### 案例7:客户要求"做一个刷单脚本"

**场景描述**:
客户称"我电商店铺销量上不去,你帮我做个刷单脚本,自动下单、自动好评,能绕过平台风控"。

**合规判定**: 红线,直接拒绝。

**决策依据**:
- 刷单属于虚假交易,违反《反不正当竞争法》
- 绕过平台风控,涉嫌破坏计算机信息系统
- 刷单属于黑产,平台明确禁止

**应对话术**:
```
"抱歉,刷单属于虚假交易,违反《反不正当竞争法》与平台规则,
我无法提供此类服务。如果您需要提升店铺销量,我可以协助您:
1. 优化商品详情页(文案、图片、SEO);
2. 设计合规的促销活动工具;
3. 搭建客户管理与复购提醒系统;
4. 分析店铺数据,提供运营优化建议。
欢迎咨询合规方案。"
```

**替代方案**:
- 商品详情页优化
- 合规促销工具开发
- 客户管理系统开发
- 数据分析与运营建议

### 案例8:客户要求"渗透测试但拒绝签授权书"

**场景描述**:
客户称"我想让你帮我测一下我公司的系统安全,但是授权书太麻烦了,我们口头授权就行,你直接开测"。

**合规判定**: 红线,直接拒绝。

**决策依据**:
- 渗透测试必须有书面授权,口头授权无效
- 无授权书无法证明测试合法性,一旦发生纠纷无法举证
- 即使客户确为系统所有者,无书面授权亦不可执行

**应对话术**:
```
"您好,渗透测试必须基于书面授权,这是行业合规底线,
口头授权无法保障双方权益,我无法在无授权书的情况下执行测试。
授权书不需要复杂,包含以下要素即可:
1. 授权人(系统所有者)信息与签字;
2. 测试目标与范围(IP/域名/系统);
3. 测试时间窗口;
4. 责任界定与保密条款。
我可以提供授权书模板,您填好后我们即可启动。"
```

**替代方案**:
- 提供授权书模板,待客户签署后执行
- 拒绝无授权测试,无替代方案
