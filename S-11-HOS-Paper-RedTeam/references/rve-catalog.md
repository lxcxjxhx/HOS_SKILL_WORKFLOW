# HOS-RVE 漏洞编号系统（Research Vulnerability Exposure）

> 仿 CVE 体系，为论文红队发现分配持久编号。**每条攻击发现必须登记，否则不算正式输出。**

## 一、编号格式

```
HOS-RVE-YYYY-NNNN
```

- `YYYY`：发现年份（如 2026）
- `NNNN`：全局递增序号（0001 起），跨论文全局唯一，按发现顺序分配

示例：`HOS-RVE-2026-0001`

## 二、分类前缀

| 前缀 | 分类 | 判定标准 | 示例 |
|------|------|----------|------|
| `RVE-DATA` | 数据问题 | 样本量、数据来源、污染、硬编码、标签质量 | 433 告警自称工业实证 |
| `RVE-BENCH` | 基准问题 | 基准挑选、可比性、过时、软柿子、泄漏 | 初始 FP>92% 的基准 |
| `RVE-EVAL` | 实验/指标问题 | 选择性报告、无基线、调参凑数、消融矛盾 | 单挑召回率遮丑 |
| `RVE-SEC` | 安全问题 | Prompt 注入、数据泄漏、Agent 逃逸、越权 | 测试数据含训练集 |
| `RVE-REPRO` | 复现问题 | 闭源、缺参数、GPU 门槛、依赖不可得 | 找不到开源实现 |

## 三、严重度

| 严重度 | 定义 | 典型场景 |
|--------|------|----------|
| `CRITICAL` | 结论整体失效或不可信 | 硬编码结果、基准泄漏、选择性报告核心指标 |
| `HIGH` | 结论被显著削弱 | 样本量过小、无基线、单来源数据 |
| `MEDIUM` | 结论部分受限 | 单语言、单厂商、缺长期稳定性 |
| `LOW` | 影响有限/改进建议 | 未报成本、未报 FPR 但影响不大 |

## 四、登记表条目结构

每条 RVE 在 `database/vulnerability.json` 中登记，结构：

```json
{
  "rve_id": "HOS-RVE-2026-0001",
  "paper_arxiv": "2602.17875",
  "category": "RVE-EVAL",
  "severity": "HIGH",
  "title": "选择性报告指标：F1 低于微调基线仍称超越",
  "layer": "experiment",
  "evidence": "摘要报告 Recall 82.7% vs 81.3%，但 F1 61.4 vs 71.6",
  "claim_ref": "Claim #2",
  "exploit": "只报召回率、隐藏 F1，结论被断章取义",
  "patch": "报告完整 P/R/F1 矩阵；按 F1 重述结论",
  "status": "open",
  "created": "2026-07-31"
}
```

## 五、分配规则

1. **触发即登记**：任何 Agent 发现值得记录的问题，立即分配编号。
2. **同论文内递增**：按发现顺序分配，允许跨类别混排。
3. **持久化**：写入 `database/vulnerability.json`，同一论文再次分析时沿用历史编号，新发现追加。
4. **不重复**：同一问题不重复编号；同一论文内同类问题可合并或分别编号。
5. **撤销**：经核实为误报的发现标记 `status: "rejected"`，编号不回收。

## 六、统计口径

月报/周报统计口径：按 `category`、`severity`、`status=open` 聚合。支持输出：
- 各分类分布（哪个层漏洞最多）
- 各严重度占比
- 高频攻击模式 TOP10（"本周最大研究漏洞 TOP10"）
- 研究机会池命中（`RVE-DATA`/`RVE-BENCH` 高频 → Research Gap）
