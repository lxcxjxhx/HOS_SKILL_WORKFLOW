# 📊 Vibe Project Score — 评分执行指南

> **版本**: 2.0.0 · **位置**: `scoring/vibe-score.md`
>
> 本文档为 AI 在执行 Vibe-Guard 评分时的操作指南。评分由 AI 推理执行，非代码执行。

---

## 评分执行流程

### 第一步：收集信息

从用户请求/项目文件中提取以下信息：

```
- 项目名称和描述
- 技术栈选择
- 项目结构（文件/目录）
- 依赖列表（package.json, requirements.txt 等）
- 是否有测试/文档/CI
- 是否有安全设计
- 是否匹配已知模板模式
```

### 第二步：逐维度评分

对六个维度分别评估，每个问题评分 `0/1/2`：

| 分数 | 含义 |
|------|------|
| 0 | 完全不符合 / 无此特性 |
| 1 | 部分符合 / 有但不完善 |
| 2 | 完全符合 / 完善实现 |

#### 🎯 领域深度（Domain Depth）

```
评估问题:
1. [权重3] 是否有超越 CRUD 的真实业务逻辑？
   - 0: 纯数据增删改查
   - 1: 有一些业务规则（如状态约束、校验逻辑）
   - 2: 有领域模型、业务规则引擎、领域事件

2. [权重2] 是否有明确的领域模型？
   - 0: 直接对数据库 CRUD
   - 1: 有 Entity/Model 层但逻辑单薄
   - 2: 有 Entity/Value Object/Aggregate + 领域行为

3. [权重2] 是否有领域事件或业务规则引擎？
   - 0: 无事件机制
   - 1: 有简单的观察者/事件
   - 2: 有完整的领域事件 + 事件处理链

4. [权重2] 是否有统一语言（Ubiquitous Language）？
   - 0: 技术术语命名（如 InsertUser, UpdateOrder）
   - 1: 部分业务术语
   - 2: 代码中业务术语一致且准确

5. [权重1] 是否使用 DDD 战术模式？
   - 0: 无 DDD 模式
   - 1: 部分使用（仅有 Entity）
   - 2: 完整使用（Entity/Value Object/Aggregate/Repository/Factory）
```

#### 🧱 架构复杂度（Architecture Complexity）

```
评估问题:
1. [权重2] 是否有清晰的分层架构？
   - 0: 单文件 / 所有逻辑混合
   - 1: 有基本分层但不严格
   - 2: 严格分层（表示层-应用层-领域层-基础设施层）

2. [权重2] 是否使用设计/架构模式？
   - 0: 无模式
   - 1: 使用 1-2 个模式
   - 2: 多个模式有机组合

3. [权重2] 是否有抽象层/接口设计？
   - 0: 直接依赖具体实现
   - 1: 部分抽象
   - 2: 依赖反转 + 接口隔离

4. [权重2] 是否有事件驱动/消息机制？
   - 0: 完全同步调用
   - 1: 简单 Pub/Sub 或回调
   - 2: 完整事件总线/消息队列

5. [权重1] 是否考虑模块化/微服务？
   - 0: 单块无模块边界
   - 1: 有模块分包/分层
   - 2: 模块独立部署/有界上下文

6. [权重1] 是否有中间件/插件机制？
   - 0: 无扩展点
   - 1: 有简单钩子/配置
   - 2: 完整插件系统
```

#### 🔁 可扩展性（Scalability）

```
评估问题:
1. [权重3] 添加新功能是否需要大量修改？
   - 2: 新增功能只需加新文件/新模块，不需修改已有代码
   - 1: 需要修改 1-2 处现有代码
   - 0: 需要重写/大量修改现有逻辑

2. [权重2] 是否有配置/策略驱动？
   - 0: 所有逻辑硬编码
   - 1: 部分配置化
   - 2: 策略模式 + 可插拔

3. [权重2] 是否有清晰接口/契约？
   - 0: 无接口定义
   - 1: 有基本类型定义
   - 2: 完整的契约测试 + 接口文档

4. [权重2] 是否考虑性能/可伸缩性？
   - 0: 无任何性能考量
   - 1: 有基本优化（索引/缓存）
   - 2: 有明确的性能目标和架构设计

5. [权重1] 是否有可插拔模块？
   - 0: 无法增加/替换功能
   - 1: 可通过配置启用/禁用
   - 2: 完整插件/模块系统
```

#### 🔐 安全性（Security）

```
评估问题:
1. [权重3] 是否有安全设计考虑？
   - 0: 完全没有安全设计
   - 1: 有基本认证
   - 2: 完整的认证+授权+加密设计

2. [权重2] 敏感数据是否加密？
   - 0: 明文存储
   - 1: 传输层加密
   - 2: 存储加密 + 传输加密 + 密钥管理

3. [权重2] 是否遵循最小权限原则？
   - 0: 全部权限开放
   - 1: 有基本角色区分
   - 2: 细粒度权限（RBAC/ReBAC）

4. [权重1] 是否有审计日志？
   - 0: 无日志
   - 1: 有基本访问日志
   - 2: 完整审计追踪

5. [权重1] 是否有输入验证？
   - 0: 无验证
   - 1: 基本类型验证
   - 2: 完整验证 + 防注入措施

6. [权重1] 是否有安全头/策略？
   - 0: 无安全策略
   - 1: 部分安全头
   - 2: CSP/HSTS/XFO/SameSite 完整配置
```

#### 🧠 创新性（Novelty）

```
评估问题:
1. [权重3] 是否与已知开源方案有本质不同？
   - 2: 完全不同的方法/架构
   - 1: 有差异化特性
   - 0: 与现有项目基本相同

2. [权重2] 是否有独特领域结合？
   - 0: 单领域标准方案
   - 1: 有跨领域元素
   - 2: 新颖的跨领域结合

3. [权重2] 是否解决了未被充分解决的实际问题？
   - 0: 已有很多成熟方案
   - 1: 现有方案有局限
   - 2: 真正的新问题或新角度

4. [权重2] 是否有新颖的技术选型？
   - 0: 标准技术栈选型
   - 1: 有非主流但合理的选择
   - 2: 创新的技术组合

5. [权重1] 是否在某维度显著优于现有方案？
   - 0: 不优于已有方案
   - 1: 在某个方面略优
   - 2: 设计目标就是超越现有方案
```

#### 📐 工程完整性（Engineering Completeness）

```
评估问题:
1. [权重2] 是否有测试？
   - 0: 无测试
   - 1: 有少量测试
   - 2: 较高测试覆盖率 + CI 集成

2. [权重2] 是否有文档？
   - 0: 无文档
   - 1: 有 README
   - 2: README + API 文档 + 架构文档

3. [权重2] 是否有 CI/CD？
   - 0: 无 CI
   - 1: 有基本 CI
   - 2: 完整 CI/CD pipeline

4. [权重1] 是否有代码规范？
   - 0: 无规范
   - 1: 有配置但未强制执行
   - 2: lint 集成 + 格式化 + pre-commit hook

5. [权重1] 是否有部署配置？
   - 0: 无部署配置
   - 1: 有 Dockerfile
   - 2: Docker + 编排 + 环境管理

6. [权重1] 是否有可观测性？
   - 0: 无监控
   - 1: 有基础日志
   - 2: 日志 + 指标 + 追踪

7. [权重1] 是否有版本管理？
   - 0: 无版本管理
   - 1: 有 changelog
   - 2: 语义化版本 + release note
```

### 第三步：计算总分

```text
各维度原始分 = SUM(问题分 × 权重) ÷ SUM(各问题最高分 × 权重) × 10

加权总分 = Σ(维度原始分 × 维度权重) × (60 ÷ Σ(维度满分 × 维度权重))
        = Σ(维度原始分 × 维度权重) × (60 ÷ 63)
        ≈ Σ(维度原始分 × 维度权重) × 0.952

其中维度权重: 领域深度=1, 架构复杂度=1, 可扩展性=1, 安全性=1, 创新性=1.2, 工程完整性=0.8
```

### 第四步：应用惩罚/奖励

```text
模板匹配 HIGH:  -15
模板匹配 MED:   -8
模板匹配 LOW:    -3
无测试:         -5
无 README:      -3
安全硬伤 HARD:  -10 (每个)
安全软伤 SOFT:  -4 (每个)

积极指标 ≥ 3 个: +5
有测试且覆盖率良好: +3
有 CI/CD:       +3
安全设计完善:   +5

最终分数 = MAX(MIN(加权总分 + 惩罚 + 奖励, 60), 0)
```

### 第五步：映射等级

```text
≥ 42: 🟢 高价值工程 — 鼓励，可选架构微调建议
28-41: 🟡 原型项目 — 提供 1-2 个升级方向
14-27: 🟠 学习项目 — 建议增加领域深度
< 14:  🔴 模板陷阱 — 触发完整选题升级建议
```

## 评分示例

### 示例 1: 用户请求「做一个番茄钟」

```text
领域深度:       2/10  (纯计时器逻辑, 无领域模型)
架构复杂度:     3/10  (单一组件, 无分层)
可扩展性:       2/10  (只能计时, 无法扩展)
安全性:         1/10  (几乎所有数据在前端)
创新性:         1/10  (已有数千个开源番茄钟)
工程完整性:     1/10  (大概率无测试/文档)

加权计算:
原始: 2×1 + 3×1 + 2×1 + 1×1 + 1×1.2 + 1×0.8 = 10.0
总分: 10.0 × 0.952 = 9.5
模板惩罚: HIGH (-15)
最终: MAX(9.5 - 15, 0) = 0

等级: 🔴 模板陷阱 (0)
操作: 完整干预 — 建议升级为行为状态建模系统
```

### 示例 2: 用户请求「做一个基于 Rust 的事件溯源框架」

```text
领域深度:       9/10  (DDD + ES + CQRS 深度领域)
架构复杂度:     9/10  (分层 + 模式组合)
可扩展性:       9/10  (事件驱动, 可插拔)
安全性:         6/10  (框架层面, 由使用者决定)
创新性:         7/10  (Rust 生态中少有的领域驱动框架)
工程完整性:     7/10  (需要补充测试和文档)

加权计算:
原始: 9×1 + 9×1 + 9×1 + 6×1 + 7×1.2 + 7×0.8 = 48.0
总分: 48.0 × 0.952 = 45.7
惩罚/奖励: 无模板 (+0), 有测试+CI 基础 (+6)
最终: MIN(45.7 + 6, 60) = 51.7

等级: 🟢 高价值工程 (51)
操作: 鼓励 + 建议补充测试和文档
```
